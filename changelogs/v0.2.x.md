# Grove v0.2.x — The V1 line

*Published June 15, 2026*

This is the release I've been working toward. `0.2.0` through `0.2.16` went out over the last week, and together they ship the V1 model I started sketching in `0.1.x`. If `0.1.x` was a proof that a file-first publishing system could work, `0.2.x` is the version I'm willing to bet the next year on.

**Highlights**

- **The V1 rewrite** — a discriminated `Resource` union (`kind: project | resource | entity`) replaces the single-shape V0 model and rewrites `validateProject` and `loadRecords` against it.
- **`generate` replaces `buildData`** as the public pipeline entry point, with `buildLlmsTxt` and `pickCleanupCandidates` joining the core API surface.
- **A real component library** — `ItemCard`, `ItemSection`, `ItemIndexRow`, `RecordSection`, `FilterGroupMenu`, `AppsPagination`, plus `Header`, `Footer`, and `BaseLayout` — all built around the new `IndexRecord` projection.
- **The Starlight plugin** lands as `@grove-dev/starlight`, the import that turns a Starlight docs surface into a Grove-backed site in one line.
- **Tailwind v4** with a `oklch()` color layer and a `--grove-*` semantic token set replaces the V0 design tokens end-to-end.
- **194 tests** across `@grove-dev/core`, `ui`, `cli`, `starlight`, plus an integration smoke for `grove new`.

## The V1 rewrite

The honest version of the V0 data model was that there was only one shape. The schema file was called `schema.ts`, but it mostly described *apps* — categories, stacks, and contributors all lived as foreign-keyed rows pointing at apps. If you wanted to publish "people" or "papers" or "playlists" through Grove, you had to bend them into apps. That worked for the directory use case, but it failed the brief.

V1 swaps the single shape for a discriminated union:

```ts
// packages/core/src/schema.ts
export const Resource = z.discriminatedUnion('kind', [
  ProjectSchema,    // kind: 'project'   — a top-level Grove project
  RecordSchema,     // kind: 'resource'  — the things a project publishes
  EntitySchema,     // kind: 'entity'    — categories, stacks, contributors
]);
```

Every record carries an explicit `kind`, and every consumer of the data — the CLI, the Astro template, the Starlight plugin, the importer — operates on `Resource` directly. `validateProject` and `loadRecords` in `packages/core/src/build-data.ts` were rewritten against the new shape; `loadRecords` now produces `records.full.json` and `records.index.json` in one pass, both shaped by the `IndexRecord` projection the UI consumes.

`buildData` is gone from the public API. The V1 entry point is `generate`:

```ts
import { defineConfig, generate, buildLlmsTxt } from '@grove-dev/core';

export default defineConfig({
  blueprint: 'project-directory',
  site: { title: 'My directory', url: 'https://example.com' },
});

await generate();           // writes data/generated/records.{full,index}.json
await buildLlmsTxt();       // writes public/llms.txt and llms-full.txt
```

This is a hard break from `0.1.x`. There are no deprecation aliases — the V0 working tree was unreleased and the rename set is intentional. If you scaffolded a V0 directory, run `grove migrate` (V1.1) or re-scaffold with `grove new`.

## A real component library

V0 shipped a long list of `templates/default/src/components/` — `Hero`, `WhyThisExists`, `MinimalAbout`, `OriginalCollection`, `ScoreBars`, `SmartLensTabs`, `AppsIndexRow`, `AppsPagination`, `AppSection`, `CategoryGrid`, `ContributorsGrid`, `ExploreByCategory`, `ExploreByStack`, `StackGrid`, `RefinePanel`, `DecisionRow`, `AppCard`. Most of them rendered rich, V0-specific UI: faceted filters, score bars, lens tabs, distribution-channel badges.

V1 deletes almost all of them.

This was a deliberate call. The V0 visual richness was real, but it was built on the V0 `OpenSourceApp` shape, and rebuilding it on `Resource` would have been a Wave 2 effort that delayed the schema work. Instead V1 ships a minimal, opinionated library that's enough to render any blueprint:

- **`ItemCard`** — the one survivor, now driven by `IndexRecord` instead of the V0 app shape. It picks up a `routeSlug` prop in `0.2.16` so the same card drives both index and detail URLs without per-page glue.
- **`ItemSection`** — a titled group of `ItemCard`s with optional "view all" link. The index page composes three of them (trending, recently added, established) and that's the whole homepage.
- **`ItemIndexRow`** — the dense row variant for the table view.
- **`RecordSection`** — the same idea, but renders the full `Record` (not the index projection) inside a detail page.
- **`FilterGroupMenu`** + **`FilterOptions`** — small primitives the index page composes for search + sort + state management, with debounce support added in `0.2.16`.
- **`AppsPagination`** — windowed pagination for the `[slug]/index.astro` page.

Layouts are just `BaseLayout`, `Header`, and `Footer`. `Header` derives its nav from `grove.config.ts → site.nav` and falls back to a sane 4-item list (Home / Browse / About / Submit) when the config doesn't override. The V0 `Seo`, `ThemeToggle`, and `SectionHeader` are gone — their concerns are absorbed into `BaseLayout` or abandoned.

The V0 components still exist as data — `ScoreBars`, `LensTabs`, `Contributors` all live in the schema — so the rich UI is a future re-introduction, not a regression.

## The Starlight plugin

`@grove-dev/starlight` (shipped during this window as `lucode-starlight` and renamed before `0.2.6`) is the answer to "what does a Grove-backed docs surface look like?" One import line:

```ts
// astro.config.mjs
import { defineConfig } from 'astro/config';
import starlight from '@astrojs/starlight';
import grove from '@grove-dev/starlight';

export default defineConfig({
  integrations: [
    starlight({ title: 'My docs' }),
    grove({ config: './grove.config.ts' }),
  ],
});
```

You get a Starlight site whose sidebar, components, and global styles are all Grove-aware. The plugin ships its own `ScoreBars`, `SidebarSublist`, and `TableOfContentsList` components in `packages/starlight/src/components/`, registers a `grove` user-config namespace, and provides a `virtual:grove-consumer-global-css` Vite virtual module so consumers' `global.css` is auto-loaded by the plugin's theme.

The plugin is unit-tested (11 cases covering `parseConfig`, `vitePlugin.resolveId`/`load`, and the `override()` slot logic). It's small enough to read in one sitting and it's the integration I expect most V1 adopters to reach for first.

## The CLI gets a workspace brain

V0's CLI was a single `init` bootstrap. V1's CLI covers the full content lifecycle:

```
grove new <name>        scaffold with blueprint + GitHub prompt
grove import <src>      awesome-list → data/records/<slug>.yml
grove validate          check records against the blueprint schema
grove generate          build data/generated/records.{full,index}.json
grove sitemap           write public/sitemap.xml
grove llms              write public/llms.txt and llms-full.txt
grove sync <github|contributors>
                        optional: enrich records with GitHub metadata
grove cleanup stale     flag records that need human review
grove build             run the framework's build command
grove dev               run the framework's dev server
```

`grove new` now asks two questions before the framework pick — **blueprint** (project-directory, resource-hub, or ecosystem-map) and **GitHub integration** (none / public metadata). The choice drives both `grove.config.ts → integrations.github` and the GitHub Actions workflows scaffolded under `.github/workflows/`. `--blueprint` and `--framework` flags short-circuit the interactive prompts for CI use.

The rename set is a hard break:

```
grove build-data         →  grove generate
grove analyze            →  grove sync github
grove review             →  grove cleanup stale
grove enrich             →  folded into grove sync github
grove build-llms-full    →  grove llms
```

The CLI itself stays framework-agnostic — it depends only on `@grove-dev/core`. Framework detection happens at `grove build` and `grove dev` time by reading the consumer project's `package.json`. As of `0.2.x`, V1 officially supports Astro only; Next.js and SvelteKit are V1.1/V1.2.

## Tailwind v4 lands

The whole design-token layer moved to Tailwind v4 with `oklch()` color values and a new `--grove-*` semantic token set. The old hex-based tokens are gone from `packages/astro/src/styles.css` and `templates/default/src/styles/global.css`; both files now consume the same `--grove-bg`, `--grove-fg`, `--grove-accent`, `--grove-card`, `--grove-border` token set.

```css
/* packages/astro/src/styles.css */
:root {
  --grove-bg: oklch(98% 0.005 250);
  --grove-fg: oklch(18% 0.02 250);
  --grove-accent: oklch(60% 0.18 250);
  --grove-card: oklch(100% 0 0);
  --grove-border: oklch(90% 0.01 250);
}

@media (prefers-color-scheme: dark) {
  :root {
    --grove-bg: oklch(15% 0.01 250);
    --grove-fg: oklch(92% 0.01 250);
    --grove-card: oklch(18% 0.01 250);
  }
}
```

The `oklch()` switch wasn't aesthetic. It was a correctness fix — Tailwind v4's color pipeline needs perceptually uniform color spaces to render gradients and dark-mode transitions consistently. Hex values gave us banded dark-mode transitions; `oklch()` doesn't.

Astro also bumped from `6.4.6` to `7.0.0` mid-window. The chip, button, and badge family in the Starlight integration got aligned to Starlight's compact pill primitive as part of the upgrade.

## The theme loader fix

The most annoying bug in the window was a Tailwind v4.3.0 comma-parsing regression that broke `:custom-variant dark` in the consumer's `global.css`. The fix landed as two coordinated changes:

1. A `virtual:grove-consumer-global-css` Vite virtual module in `packages/astro/src/integrations/grove-theme.ts` that auto-loads the consumer's `global.css` instead of relying on import order.
2. Splitting the `:custom-variant dark` selector out of the comma-separated selector list at the top of `styles.css` so the v4.3.0 parser doesn't choke on it.

It's the kind of fix that doesn't show up in the changelog unless you were the person whose site was rendering as a wall of unstyled HTML. If that was you — sorry, and it's fixed in `0.2.6` and later.

## Tests arrive

The `0.1.x` line shipped with a smoke test for the CLI scaffold and a few handwritten cases. `0.2.x` adds a real test layer:

- **`@grove-dev/core`** — 91 cases across 8 files (`slug`, `health`, `decisions`, `validate`, `enrich`, `github`, `github-client`, `importer`, `build-data`). The `health.test.ts` cases pin the maturity-ladder boundaries (184 / 548 / 730 days) because `applyDecision` in `build-data.ts` reuses the same logic.
- **`@grove-dev/ui`** — 75 cases across `filter`, `sort`, `scoring`, `paginate`, `format`. The `paginate.test.ts` pins the contract that out-of-range and `NaN` page indices return `[]`, not page 1.
- **`@grove-dev/cli`** — 15 cases around the template loader, including a regression guard for the `parseDeployProvider` silent-fallback bug.
- **`@grove-dev/starlight`** — 11 cases for the plugin's `parseConfig` and `override()` slot logic.
- **Integration smoke** — `tests/integration/grove-new.test.ts` runs `grove new test-tmp --yes --framework astro --deploy none --no-git --no-install` in a temp directory and asserts the expected file set exists.

`pnpm test` runs 194/194 cases. Coverage is around 52% statements, 54% lines — the templates and CLI command wiring are still uncovered, which is fine for V1 but is the obvious next investment.

## Astro 7 and the V0 cleanup

The Astro major-version bump (`6.4.6` → `7.0.0`) and the V0 cleanup landed together. The Starlight integration's chip / button / badge family was aligned to Starlight's compact pill primitive to match. `BaseLayout.astro` absorbed the V0 `Seo.astro`, `ThemeToggle.astro`, and `SectionHeader.astro` concerns, then `4b4f9a8b` removed the deprecated V0 landing and showcase pages and promoted the Starlight MDX index as the public surface.

If you're tracking the commit history, the V0 → V1 transition is most visible in `a39c0ff1`: 18 components deleted, 1 layout slimmed, 1 layout kept. It looked brutal in `git diff --stat` and it was the right call.

## What's next?

The next release is **v0.3.x**, and the headline is that V1 turned out to be too big for one shape. The next chapter splits V1 into a directory toolkit that consumers own and a thin Astro site that ships with it.

What you'll see when v0.3.1 lands:

- **Grove is now a directory toolkit.** New `@grove-dev/core/directory` subpath (`directory-search`, `directory-lenses`, `directory-display`, `directory-format`, `directory-scores`, `directory-repo`, `directory-taxonomy`, `directory-client`) replaces the V1 mega-bundle. `packages/{nextjs,svelte,ui}/` and `packages/astro/templates/default/` are removed.
- **The CLI narrows to four commands.** `init`, `check`, `sync`, `cleanup`. The other V1 commands (`validate`, `generate`, `sitemap`, `llms`, `build`, `dev`) collapse into `check` or move into the build pipeline.
- **Apps move to `apps/`.** `docs/` becomes `apps/docs/`, `site/` becomes `apps/example/`. Pages are now consumer-owned — they live in the consumer's repo, not in the package.
- **The docs site gets a real home.** `apps/docs` is rewritten with a 3-tier framework matrix, OG/Twitter/JSON-LD metadata on every page, SEO + PWA assets, and a canonical domain switch to `grove.dev.mn`.
- **JSON-LD you can trust.** The invalid `SearchAction` target drops, `Lucode` becomes `Grove Starlight`, and the org rename `grove-dev/grove` → `tortuvshin/grove` lands.

If you upgraded to v0.2.x expecting the V1 component list to grow, you'll find the surface has shrunk on purpose. v0.3.x is the line where Grove stops trying to be a CMS and starts being a toolkit.
