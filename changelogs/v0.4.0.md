# Grove v0.4.0

*Published July 25, 2026*

I'm excited to ship Grove v0.4.0 — the release where two new ideas stop being experiments and start being the product. We turned filter URLs into curated pages, and we made site quality a thing you can run from the CLI. Around those two headlines we shipped a real README generator, a unified machine-readable page contract, a licenses taxonomy, and 25 fewer transitive vulnerabilities.

**Highlights**

- **Collections**: a first-class engine that turns a query (`?stack=flutter&category=finance`) into a curated, ranked, indexable page — plus `grove collection promote` to freeze it as YAML.
- **`grove audit`**: a Lighthouse 100×4 gate (four categories × runs) that walks a 7-page manifest and exits non-zero when budget is broken.
- **`llms-full.txt`, `robots.txt`, sitemap index**: first-class generators behind a unified `PageDocument` contract.
- **`grove readme generate`**: a sindresorhus/awesome-format README writer that injects between sentinels so hand-written intros survive regeneration.
- **Licenses taxonomy**: a curated `licenses: string[]` field on every record, six SPDX entries in `data/taxonomy/licenses.yml`, and a matching `licenses/[name].astro` page.
- **25 audit vulnerabilities resolved** via pnpm overrides across the workspace.

## Collections

The headline feature is one we've been circling for a while. Until now, every list Grove could render was either a hand-written taxonomy page or a live filter URL — and the two never agreed about what "done" looked like. A `?stack=flutter&category=finance` URL was a transient view; it disappeared the moment you changed the query. A taxonomy page was a static file that nobody owned. There was no middle ground for "I found a good filter, and I want to keep showing it."

v0.4.0 adds that middle ground. `packages/core/src/collections.ts` defines `Collection` as a typed object with a `query`, a `ranking`, and optional `seo`/`editorial` blocks. `runCollection` joins the query against validated records, applies ranking (a `quality` preset plus custom recency/star weights), and emits a stable list. `findRelated` walks sibling collections and returns entries that share query keys — useful for "Related lists" footers without writing another filter by hand.

The Astro side has matching routes: `pages/collections/[slug].astro` renders a single curated collection; `pages/collections/index.astro` lists them all. `CollectionPage` consumes the typed payload, `CollectionRow` and `CollectionTeaser` keep the visual contract consistent with the rest of the framework, and `GroveDocumentHead` emits the canonical and `twitter:creator` meta from the same `PageDocument` the page is built on. One source of truth, many surfaces.

The bit I'm most pleased with is the CLI. `grove collection promote` takes a filter URL and writes a curated collection YAML — same query, frozen as content:

```bash
grove collection promote \
  --from "/browse?stack=flutter&category=finance" \
  --slug top-flutter \
  --title "Top Open Source Flutter Apps"
```

`packages/cli/src/collection-cli.ts` parses the URL with `URLSearchParams` (so `&` and `=` in values round-trip correctly), maps query keys to the collection schema, defaults `ranking.preset` to `quality`, and writes to `data/collections/<slug>.yml`. Two follow-up commits caught the obvious paper cuts — `mkdir data/collections` before the write, and `loadCollections` only swallowing `ENOENT` so a malformed YAML surfaces as an error instead of a silent empty page.

`apps/example` ships two promoted collections to prove the contract: `top-flutter.yml` (Flutter apps ranked by quality) and `top-ai-agents.yml` (Python agent frameworks, with an `editorial.selectionNote`). Both land as real pages, both are discoverable from `/collections`, and both pick up the framework's standard card treatment after the alignment pass.

## `grove audit`

The second headline is the one I expect to change how people use Grove day-to-day. We have always cared about performance and accessibility — the example site looks the way it does on purpose — but there was no way to prove that care survived the next commit. Until now, "is this site still fast?" was answered by opening Lighthouse in a browser tab and squinting.

`grove audit` closes that loop. It reads `grove.config.ts`'s `audit.pages[]` manifest, launches Chrome, runs Lighthouse against each page across both `mobile` and `desktop` profiles, repeats for the configured number of runs (default 3, max 5), and evaluates the results against a `100×4` budget: 100 in each of performance, accessibility, best-practices, and SEO. Any page that drops below 100 in any category fails. The CLI exits non-zero, prints a one-line per-violation report, and can write JSON or JUnit XML for CI.

```bash
grove audit --runs 3                 # full sweep, default profiles
grove audit --desktop --page /       # only the home page, desktop only
grove audit --json reports/lh.json   # machine-readable report
grove audit --junit reports/lh.xml   # CI-friendly JUnit
```

A few pieces matter more than they look. `loadManifest` handles `export default defineConfig({...})` so audit works with whatever config style people happen to use. `evaluateBudget` exempts 404 pages from the budget — a 404 is allowed to fail performance — and the a11y issues that surfaced in the first audit run against `apps/example` were fixed before the manifest was wired up so the gate is actually green for the reference site.

The manifest itself is a small but meaningful contract. Seven page types are recognised: `home`, `directory`, `collection`, `record`, `content`, `empty`, and `404`. Every one is declared explicitly in `grove.config.ts` with its expected profile and budget. The CI workflow at `.github/workflows/lighthouse-audit.yml` runs weekly and on demand, invokes the built CLI directly (no `pnpm start` race), and restricts its permissions to read-only.

End-to-end coverage exists: `tests/integration/grove-audit.test.ts` boots `apps/example`, points Lighthouse at `127.0.0.1`, and asserts the budget holds. Unit tests cover the helpers, and `reference/audit.md` documents the manifest contract and exit codes so you can wire it into your own pipeline without reading the source.

## `llms`, `robots`, sitemap

The third headline is a quiet one and probably the most consequential over time. Until now, the machine-readable surface of a Grove site was a happy accident: `llms.txt` was emitted by `core`, `robots.txt` was an Astro route that someone had to remember to add, and the sitemap was whatever Astro's `@astrojs/sitemap` integration happened to produce. Three generators, three contracts, three chances to drift.

v0.4.0 introduces `PageDocument` — a typed, JSON-LD-validated object that every generator consumes. `packages/core/src/page-document.ts` defines the shape (canonical URL, title, description, structured data payload, indexing policy); `page-document.test.ts` enforces it; the JSON-LD registry validates `@context` and required fields before anything downstream sees the page.

Three generators sit on top of it:

- **`llms-full.txt`** (`buildLlmsFullTxt`) — the full-text companion to `llms.txt`, intended for LLM ingestion. Dispatch is keyed off the `kind` discriminant (not config presence, after a bug where the wrong builder ran when `llms.txt` was disabled), and the output is plain Markdown so model tokenizers don't waste budget on HTML.
- **`robots.txt`** (`buildRobotsTxt`) — generated from a filter URL index policy. If you mark `?stack=foo` as non-indexable, that policy flows through to robots and to `noindex` meta tags. The fix that landed with it removed a catch-all pattern that was flagging canonical paginated URLs as duplicates — a real bug that would have silently de-indexed working pages.
- **Sitemap index** (`buildSitemapIndex`) — XML-escapes the base URL (a real fix, since the previous version broke on any URL containing `&`), generates a proper `<sitemapindex>` document, and emits per-section sitemaps as siblings.

All three are routed through `buildSiteArtifacts`, which is the single place to look if you want to add a fourth. That's the contract: every machine-readable surface reads from `PageDocument`, every generator is wired into `buildSiteArtifacts`, and `GroveDocumentHead` consumes the same `PageDocument` to render `<title>`, OG tags, and `twitter:creator`. One schema, many outputs — the mental model the whole project runs on.

## Licenses everywhere

Licenses had been the missing taxonomy for two minor releases. `ProjectRecord` already knew about `github.license`; what it didn't have was a curated `licenses: string[]` field, a taxonomy YAML, or a page route.

`packages/core/src/schema.ts` gains the field; `filterRecords` checks the curated array first and falls back to `github.license` when no curated value is present (so existing sites keep working without edits). `data/taxonomy/licenses.yml` ships six SPDX entries: `mit`, `apache-2.0`, `gpl-3.0`, `bsd-3-clause`, `apache`, and `bsd`. All six example records gain `licenses: [mit]`.

The shared component is `TaxonomyList.astro` — same body for stacks, categories, and licenses pages. `pages/licenses/[name].astro` and `pages/categories/[name].astro` mirror the existing `pages/stacks/[name].astro` pattern: filter, render, link back. A parity test walks all three pages and asserts they share the same SEO and structure, so the next taxonomy page we add won't quietly drift.

## README generator

The example site is an awesome-list; it has always been embarrassing that the README was hand-maintained. v0.4.0 fixes that.

`packages/core/src/awesome-readme.ts` is a canonical sindresorhus/awesome-format writer. It reads `data/records/*.yml`, groups by `data/taxonomy/categories.yml`, sorts alphabetically within each section, filters by visibility, prefers the homepage URL over the repo URL, and renders the result between two sentinels: `<!-- grove-readme:start -->` and `<!-- grove-readme:end -->`. Hand-written intros and contribution guides above the start sentinel survive regeneration; everything between is owned by Grove.

`grove readme generate` is the CLI front door. Three flags matter:

```bash
grove readme generate             # write to README.md
grove readme generate --stdout    # print to stdout (CI dry-run)
grove readme generate --check     # exit 1 when out of date
```

`--check` is the interesting one. It runs the full pipeline, compares the rendered block against what's on disk, and exits non-zero on drift — so a README generator ships with a regression net, not just docs.

An optional `readme:` block in `grove.config.ts` lets curators override the preamble (title, tagline, browse link, intro, badge/TOC visibility) without forking the generator.

## Docs alignment

A lot of the work in this release was catching the docs up to what Grove actually is. For a few minor releases, the landing page, the docs site, and the package READMEs had drifted apart — references to packages that don't exist, CLI commands that were renamed, framing that emphasised directories over the system underneath. v0.4.0 is the release where the docs start describing the product again.

The reference site picked up a single CLI table covering the eight shipped commands (`init`, `check`, `sync github`, `sync contributors`, `cleanup`, `audit`, `collection promote`, `readme generate`). Ghost commands were scrubbed from `reference/build/customize/automation/guides/concepts/showcase`. The home page sections were rewritten to match v0.4.0 reality: `grove new` became `grove init`; the four-stage pipeline card collapsed `Enrich` and `Review` into a single `grove check`; the framework grid replaced `@grove-dev/ui` (which doesn't exist) with `@grove-dev/starlight`. The roadmap was rewritten against the actual four published packages; Next.js and SvelteKit adapters were demoted to "planned."

If you read the docs and something doesn't match the CLI, that's now a bug. Please open an issue.

## Security hygiene

`pnpm audit` had been quietly complaining for a while. v0.4.0 resolves 25 transitive vulnerabilities through a small set of pnpm overrides, plus one targeted version constraint.

The high-severity list is the one worth reading:

- `sharp <0.35.0` — four libvips CVEs in the image pipeline.
- `js-yaml <4.3.1` — YAML merge-key quadratic CPU consumption.
- `svgo <4.0.2` — `removeScripts` plugin executable-scripts bypass.
- `fast-uri <3.1.5` — host confusion via backslash authority.
- `postcss <=8.5.22` — path traversal via `sourceMappingURL`.
- `brace-expansion <2.1.4` — DoS via unbounded expansion.
- `astro <7.0.6` / `<7.0.4` — XSS via `transition:*` directive on islands.

Moderate: `ip-address <=10.3.0` (SSRF / CIDR suffix classification bypass) and `@opentelemetry/core <2.8.0`. The `js-yaml` override is constrained to the `4.x` range (`c280275b`) so we don't accidentally jump majors when upstream bumps. A pnpm-not-found race in `setup-node@v7` is fixed in CI (`c275e663`), and the unit-test workflow now builds `apps/example` and the full workspace tree before running tests so the build is reproducible from a clean checkout.

This isn't glamorous work, but it compounds. Twenty-five fewer ways for a CVE scanner to fail CI, and the project is now small enough that the override list fits on a screen.

## Smaller things worth knowing

A few changes that didn't make the headline list but matter:

- **`Astro.site` is required** for canonical URL construction in collection routes. Missing config is now an error, not a silent wrong URL.
- **Sync preserves curator fields** and extracts a wider set of GitHub metadata on each run, so `grove sync github` doesn't accidentally overwrite an editor's hand-curated notes.
- **`twitter:creator` meta** is now rendered in `GroveDocumentHead`.
- **`v0.5.0` scope was drafted** while v0.4.0 was baking, so the next release has a clearer shape than this one did.

## v0.4.1

Published the same day as v0.4.0. A small hotfix landed about an hour after the initial release — I caught a regression in the `grove audit` IPv4 host selection on the integration test runner and shipped `0.4.1` rather than muddy `0.4.0`. Nothing else changed; if you grabbed `0.4.0`, the upgrade is a no-op.

## What's next?

The `v0.5.0` scope is drafted and the work is already in flight:

- **Next.js and SvelteKit adapters** — both are scaffolds today; the goal is full directory parity with Astro.
- **A real `grove import`** command for turning arbitrary GitHub repos and awesome-list READMEs into `Resource` records without a hand-written YAML step.
- **More `PageDocument` consumers** — OpenGraph images, structured-data QA, and per-page meta overrides.
- **A wider audit manifest** — currently seven page types; the goal is to recognise the full taxonomy so every site can declare its expected surface.
- **Docs as a product surface**, not an afterthought — the alignment work in v0.4.0 was a down payment on keeping the site honest.

If you've been waiting for collections or audit before trying Grove, this is the release. Both work end-to-end on the example site today.
