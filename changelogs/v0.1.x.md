# Grove v0.1.x

*Published June 9, 2026*

I'm excited to ship the first public releases of Grove — a small, file-first publishing system for structured knowledge. v0.1.1, v0.1.3, v0.1.4, and v0.1.5 went out to npm this week. They are early, opinionated, and ready to be poked at.

**Highlights**

- **A monorepo of six `@grove-dev/*` packages**, versioned and published together: `core`, `ui`, `astro`, `nextjs`, `svelte`, and `cli`.
- **A schema-first data model** in `@grove-dev/core`: a discriminated `Resource` union, importers, validators, taxonomy, and a build pipeline that turns folder-shaped content into derived outputs.
- **A working `grove new` CLI** that scaffolds an Astro, Next.js, or SvelteKit project with interactive prompts, then drops in a real example dataset.
- **An Astro template** rendering a polished directory site out of the box — filters, pagination, score bars, lenses, hero, contributors, and a tailwind theme.
- **A one-command release flow** (`pnpm release`) that builds, bumps, and publishes in dependency order.

## A data model that lives in files

The first commit of Grove already had the thing I cared about most: a data model that lives in files. No database, no admin UI, no runtime server. You put YAML and Markdown in a directory and `@grove-dev/core` decides what it means.

`packages/core/src/schema.ts` defines `Resource` as a discriminated union — `App`, `Category`, `Contributor`, `Stack`, `SiteStats` — so every record in your project is one well-typed shape. Importers turn whatever you have (`awesome-list` README, GitHub metadata, plain Markdown) into that shape. `validate.ts` runs Zod against the result and tells you exactly which fields are wrong. `build-data.ts` joins, deduplicates, and produces the data the templates consume.

The mental model is intentionally small:

```
data/
  records/        # YAML or Markdown per record
  taxonomy/       # categories, stacks, lenses
  site.config.ts  # one config object
```

One piece of content, many outputs. The same record feeds a directory page, a JSON dataset, an `llms.txt`, an OG image, and structured data — without re-entering it per surface.

## A CLI that scaffolds a real site

The biggest thing I wanted to ship was a CLI that doesn't pretend. `grove new` asks three questions — project name, framework (Astro, Next.js, or SvelteKit), deployment target — uses `@clack/prompts` for a friendly flow, then copies a working template into a new directory.

The hard part was making the template loader honest about what it knows. `packages/cli/src/template-loader.ts` resolves a template by framework + deployment combo, applies the project's name and chosen target, and writes a runnable scaffold. A small smoke test in `scripts/test-scaffold.mjs` runs the whole thing in a temp directory and asserts the resulting project builds, so we don't ship a CLI that quietly produces broken starters.

```bash
pnpm dlx @grove-dev/cli new my-directory
cd my-directory
pnpm install
pnpm dev
```

That's the whole loop. You go from zero to a populated site in under a minute.

## An Astro template that doesn't look like a starter

I have a strong opinion about starter templates: they shouldn't look like starters. `templates/default/` ships with a real example dataset, a `Hero`, `ItemCard`, `Filters`, `Pagination`, `ScoreBars`, `LensTabs`, `RefinePanel`, and a `Contributors` grid — all styled with Tailwind and a default design token set.

`packages/astro/src/components/ItemCard.astro` is a good example of the philosophy: it consumes the validated `Resource` from `@grove-dev/core` and renders the same way whether the data came from `data/records/` or from a remote source. The template doesn't care where the records came from. That's the whole point of having a `Resource` union upstream.

The Next.js and SvelteKit adapters ship smaller scaffolds for now — enough to prove the data flows through, with the full directory UI as a near-term goal.

## A release script that respects the dependency graph

Shipping six packages by hand was already painful on day one. `scripts/release.mjs` (added in 0.1.4) does it correctly: it builds in topological order (`core` → `ui` → `{astro, nextjs, svelte}` → `cli`), bumps versions in lockstep, and publishes. It supports patch / minor / major, explicit versions, and `--dry-run` so you can rehearse a release without touching npm.

```bash
pnpm release --minor         # 0.1.x → 0.2.0
pnpm release --bump=0.2.0    # explicit
pnpm release --dry-run       # build + bump + dry publish
```

This isn't glamorous work, but it's the kind of tool that compounds: once you trust `pnpm release`, you ship more often, and shipping more often is how a small project stays alive.

## What's next?

A few things are already in motion and will land in the next few releases:

- **A real website.** The template renders well, but the public grove.dev needs its own surface — docs, examples, and a changelog feed that's actually readable.
- **Better tests.** The core has solid unit coverage; the adapters need the same.
- **More importers.** A README parser is already in `core/src/parseReadme.ts`; I'd like a Notion and an Airtable bridge next.
- **Per-package overrides** for things like `outputs` and taxonomy, similar to how Turborepo's `pipeline` grew.
- **A landing page you actually want to send people to**, instead of just the README.
