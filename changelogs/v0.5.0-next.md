# Grove v0.5.0-next is out

`v0.5.0-next.2` is now tagged `latest` on npm. This is a prerelease line — we're using the `-next` channel to ship the v0.5.0 surface iteratively before cutting a stable tag. Everything in this post is shipping behind that channel.

**TL;DR**

- **Record detail pages**: the first major feature lands. Rich markdown, screenshots, summaries, source descriptions, sidebar collection membership, and tag-facet chips — all lifted into `@grove-dev/astro`.
- **Landing-page rewrite**: the homepage was rebuilt around a quieter hero, a three-card grid, and a dedicated `--grove-card` background token. Iteration is visible in the diff.
- **Comprehensive v0.5.0 audit fixes**: XSS hardening in Starlight components, a Shiki theme swap for WCAG AA contrast, SPDX license display, bot filtering, and dozens of test/tooling improvements.
- **`grove import`**: the awesome-list ingestion flow that already lived in `@grove-dev/core` is now a first-class CLI command.
- **AGENTS.md**: we wrote down the product principles, the architecture guardrails, and the mental model — and symlinked `CLAUDE.md` to it.
- **Docs restructure**: a 12-section sidebar replaces the old guide pile, with new sections for blueprints, sources, outputs, deployment, architecture, and FAQ.

That's ~17.7k insertions and ~6.9k deletions across 259 files. Read on for the story.

---

## Landing rewrite

The headline change in this line is the landing page. Not because it's the most code, but because it forced us to decide what Grove actually is, on a single page, in front of a stranger.

Before this rewrite, the homepage leaned on a "Problem / HowItWorks / Health / Integrations / Build" component stack that read more like a feature inventory than a story. The hero carried a hard-coded "Lighthouse 100" claim that wasn't backed by anything reproducible. Card backgrounds reused the page background, so sections blurred into each other. The lens panels — three sections meant to show different facets of the directory — were quietly rendering the same six apps in all three slots because `getHomePageModel` was filtering by the wrong field.

We replaced that with a focused structure: a quieter Hero (focal-first, no false claims, names the actual `grove audit` workflow), a shared `CardGrid`/`CardIcon` so every card in the system reads as one system, and a dedicated `--grove-card` token (`#141516`) so cards actually lift from the page background. The lens panels got distinct filters so each panel shows a different cut of the data. Contributor counts went away from the hero — they were noise.

```css
/* packages/astro/src/styles.css */
:root {
  --grove-card: #141516;   /* both light and dark schemes */
}
```

The Demo component got the most iteration: continuous progress bar, smooth opacity transitions across the step rail, animation parameter fixes for the file-tree and system-diagram panels, and new test cases for the `deploy` and `automate` steps. There was a brief detour where `LandingHero` and `ProjectCard` were introduced, wired into the example, then reverted because the simpler three-card grid + centered hero composition was stronger. You can see the back-and-forth in `02e5a9b0`, `9349b64f`, `f3a06e09`. The final shape — three cards under a centered hero — stuck.

I won't pretend the rewrite was linear. It wasn't. But the result reads as one page, not five stacked sections.

## Record detail pages

This is the first major feature of the v0.5.0 line, and it's the change that justifies the prerelease cadence on its own.

Until now, every detail view was rendered by `apps/example`. That worked for one site; it didn't scale to anyone consuming `@grove-dev/astro` as a package. The whole rendering pipeline now lives in the package: `RecordHeader`, `RecordSidebar`, `TableOfContents`, `MarkdownBody`, `EditorialSummary`, `LanguageBreakdown`. The package owns the markdown-to-safe-HTML pipeline — Shiki dual-theme, `sanitize-html` with `allowedStyles`, custom heading-id slug rules.

The markdown pipeline got richer. `renderMarkdownToSafeHtml` replaces a narrow allowlist (h1-h4, p, lists, code, blockquote) with the full CommonMark + GFM surface: h1-h6, tables, images, task-list inputs, `details`/`summary`, `kbd`, `mark`, `sub`/`sup`, `abbr`, figures. Heading anchors are emitted via `uniqueSlug`, so the on-page TOC sidebar deep-links correctly. Tables wrap in `.grove-prose-table-wrap` so overflow stays inside a rounded border instead of breaking the layout. Sanitization got an explicit `span[style]` rule that closes a `url(javascript:)` bypass through Shiki CSS variables — only `--shiki-*` and color values pass.

A few small schema fields landed alongside the renderer:

- `screenshots[]` — a gallery component renders a record's screenshots as a horizontal strip. Useful for design tools, dashboards, anything visual.
- `summary` and `sourceDescription` — short editorial blurb plus a "where this came from" note. `EditorialSummary` gets a real heading now (was a div).
- "Also in: …" sidebar block — when a record belongs to multiple collections, the sidebar lists each collection so a reader can cross-navigate.
- Tag chips on detail pages link to the **tag facet**, not full-text search. This was a quiet but real fix — chips that landed you on a search results page were noise.

The example app is now a slim consumer. `5d9cee33` deleted its local rendering in favor of the package's components, then `ee63d47d` added a rich CrewAI markdown that exercises every supported element (headings, tables, task lists, kbd, details/summary, the works) so future regressions surface in tests.

## Comprehensive v0.5.0 audit fixes

We ran a full audit before starting v0.5.0. The findings landed in `AUDIT.md`. The fix commit (`1f8a005a`) closes all of them. Highlights:

**XSS in Starlight components (HIGH).** The Starlight `PageFrame` footer was running `marked.parseInline(...)` and piping the result through `set:html`. Same for `Hero` title/tagline and `Card` title — all of them were taking Zod-validated frontmatter strings and rendering them as raw HTML. They're now plain text interpolation, which means auto-escaping. `image.html` and `icon.html` keep their raw-HTML affordances — they're documented, and content authors opt in knowingly.

**`Seo.astro` silent fallback (MEDIUM).** When `Astro.site` was missing, the SEO component fell back to `https://example.com` and quietly polluted canonical URLs, OG tags, Twitter cards, and JSON-LD. It now throws a clear build error. Anyone who hits this in CI will know exactly why.

**`robots.txt` sitemap mismatch (MEDIUM).** `robots.txt` pointed at `sitemap-index.xml`. The build emits `sitemap.xml`. Mismatch. Fixed.

**`SubmissionClient` rate-limit leak (MEDIUM).** The visitor's browser was hitting `api.github.com` directly, which meant every visitor burned the per-IP 60/hour unauth rate limit and leaked the visitor's IP. There's a new `fetchRepoMetadata` helper in `@grove-dev/astro/server`; consumers wire their own `/api/github-repo` endpoint, configurable via `githubProxyPath` prop.

**`Shiki` dark theme contrast.** Swapped to `github-dark-default`. Old theme failed WCAG AA on some inline-code/background pairs. The highlighter is also now cached on `globalThis` with a regression guard (`0237a8d1`) — a warning that fired on every `astro dev` save ("140 instances have been created") is gone.

**Bot filtering.** Contributor sync and render both filter bot accounts out. Previously the example app showed a `dependabot[bot]` line under contributors, which read as unmaintained.

**License display.** A new `licenseDisplay` helper neutralizes SPDX placeholders like `NOASSERTION` and `UNKNOWN`. License filter logic (case-insensitive, curated-array precedence over GitHub fallback, explicit empty suppresses fallback) lives in both `filterRecords` and `filterEntries`. Seven license filter tests pin the behavior.

**Facets.** The Tag dropdown is now curated against `data/taxonomy/topics.yml` — no more freeform tag spam from importers. When other filters are applied, intersection counts are shown so a user can see how many records would remain after applying the next filter.

**Pagination iteration.** We added server-side pagination for the SSR card markup (`f8ba6207`) and reverted it (`b3496c4d`) once we measured the trade-off — it pushed complexity into the SSR path without enough payoff at current record counts. The intent lives in the diff and we'll revisit when record counts justify it.

**Schema.org on collections.** Collection pages now emit `ItemList` JSON-LD. Small thing; matters for search engines reading the site as structured data.

## AGENTS.md and the product principles

We added `AGENTS.md` (`6995f29a`), then tightened it (`1a4ed497`) and symlinked `CLAUDE.md` to it. The file is short on purpose. It defines what Grove is, what it isn't, and the architecture guardrails.

The mental model is one line: *maintain structured knowledge in files; Grove publishes it into useful human- and machine-readable outputs and keeps everything in sync.* Everything else — the product principles, the "what Grove is not" list, the guardrails — flows from that.

> A directory is one possible use case — not the product definition.

That sentence earned its place. Without it, every contributor (and every AI assistant) starts optimizing Grove toward a directory starter. With it, we have a test: if a change would make Grove a better directory but a worse file-first publishing system, the change loses.

The guardrails are short and concrete:

- Preserves file-first ownership.
- Supports static publishing and portability.
- Improves publishing, synchronization, or maintenance.
- Works across Grove use cases, not just one.
- Does not introduce unnecessary database or server requirements.

If a PR doesn't clear all five, it gets pushed back. The v0.5.0 audit was the first end-to-end test of these guardrails and they held.

## `grove import`

The parser and writer already shipped in `@grove-dev/core` (`importAwesomeList`, `writeImportedRecords`). They were only callable from a script. `6bee0014` wires them behind a top-level CLI command:

```bash
grove import https://github.com/sindresorhus/awesome
```

Source precedence: a URL matching `https://github.com/<owner>/<repo>` is rewritten to the raw README before fetching; any other `http(s)` URL is fetched as-is; anything else is resolved as a local path. Records land under the configured `paths.recordsDir` for the site's blueprint and are tagged `source: { type: 'import' }` so curators can filter imported vs. hand-authored records.

This is the v0.5.0 roadmap item that lets a new site bootstrap from an existing awesome-list in one command, then edit the resulting YAML by hand — which is exactly the file-first flow we want.

## Categories and stacks index pages

`f98dad6f` adds top-level `/categories` and `/stacks` routes in the example app. The header nav now links to a full taxonomy index with live counts; each tile opens the existing `/categories/<id>/` and `/stacks/<id>/` browse pages pre-filtered. The reference taxonomy pages (stacks, categories, licenses) all use `BaseLayout` + `Seo` + a shared polished card-grid pattern that matches the example's `TaxonomyList.astro`, and a new `page-parity.test.ts` pins SEO + page-structure alignment so the package and the example can't drift apart.

## A new docs spine

The docs site was a pile of guides that overlapped. `ea4e5df2` restructured `apps/docs/` around the file-first mental model: a 12-section sidebar (Introduction, Getting Started, Records & Blueprints, Sources, Generated Outputs, Customize, Automation, Deployment, Reference, Architecture, FAQ, Project) with new sections for `blueprints/`, `outputs/`, `sources/`, `deployment/`, `architecture/`, and `faq.md`. Deprecated packages (`@grove-dev/nextjs`, `@grove-dev/svelte`) were removed from the sidebar; `guides/`, `build/`, and the old `concepts/blueprints` page were folded into the new structure.

Roughly 2,500 lines of new content landed: an `introduction.md` that walks through source content → Grove → multiple outputs, a `concepts/philosophy.md` with a comparison table, three blueprint pages (project directory, resource hub, ecosystem map), six source pages (records, taxonomy files, collections, decisions, content pages, health classification), four output pages (overview, llm, seo, site-meta) covering `llms.txt`, `ai.txt`, sitemaps, JSON-LD, OG images, webmanifest, and `security.txt`, four deployment pages (GitHub Pages, Cloudflare, Netlify, self-hosted), and three reference pages (api-core, plugin-author-guide, migration).

The sidebar-coverage script now checks both directions (slug → file AND file → slug). Zero orphans across 60 slugs. If a contributor adds a page that isn't in the sidebar, or a sidebar entry without a page, CI catches it.

## What's next?

**Stable `v0.5.0`.** That's the next stop. The `-next` channel exists so we can ship the surface iteratively and catch regressions in the wild before tagging a stable. Once we have a quiet week on the prerelease line and the audit gates stay green, we cut `v0.5.0` from this branch and the prereleases stop being `latest`.

The deferred items I'd like to close before that cut:

- **OIDC trusted publishing** for the npm release pipeline. We're a single-maintainer project today, but the moment a second person can publish, the long-lived npm token stops being acceptable.
- **Activity-badge color-contrast verification** — needs a real Lighthouse run against `apps/example` to confirm the four tones pass WCAG AA on the actual surfaces they'll render on.
- **OG-image generator** in `@grove-dev/astro` so consumers don't have to roll their own. The detail-page metadata contract is in place; the image side is the obvious next layer.
- **Revisit server-paginated SSR card markup** once a real site crosses a record-count threshold that justifies the complexity. The add+revert cycle in this release told us the cost; we don't pay it again until the data warrants.

If you're building on `-next`, please file issues against the prerelease tag. That's the whole point of the channel — every report you file shortens the time to `v0.5.0` stable.
