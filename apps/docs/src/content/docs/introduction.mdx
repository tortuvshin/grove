Grove is a **file-first publishing system for structured knowledge**.

You write the source of truth — YAML records, Markdown bodies, taxonomy files. Grove
publishes it into a coordinated set of human- and machine-readable outputs, and keeps
them in step with the files as they change.

<Aside type="tip" title="The Grove mental model">
  Maintain structured knowledge in files. Grove publishes it into useful human- and
  machine-readable outputs and keeps everything in sync.
</Aside>

## One record, many outputs

Add `data/records/my-project.yml` and run a build. That one file becomes all of this,
without you writing any of it a second time:

| Output | Where it lands | Who reads it |
|---|---|---|
| A detail page | `/projects/my-project/` | People browsing the site |
| A row in the browse index | `/projects/` | People filtering and searching |
| A sitemap entry | `public/sitemap.xml` | Search engines |
| A `SoftwareSourceCode` block | inline JSON-LD on the page | Google rich results |
| An index line and a detail section | `public/llms-full.txt` | AI assistants and crawlers |
| A social card | `public/og/records/my-project.png` | Slack, LinkedIn, Discord |
| A row in the dataset | `data/generated/records.json` | Anything consuming your data |

Rename the file and the slug follows. Delete it and every one of those outputs
disappears with it. Nothing is stored anywhere else, so nothing can drift out of step.

The same loop applies to taxonomy entries, collections, decisions, and standalone
content pages.

<Aside type="note" title="What lands where">
  `llms.txt` is the small file — site name, tagline, and counts. The per-record index
  lines and detail sections go in `llms-full.txt`. JSON-LD type varies by record kind:
  `SoftwareSourceCode` for projects, and `Article`/`Book`/`Course`/`Person`/
  `Organization` and friends for the other kinds.
</Aside>

## Static-first, no runtime

There is no server, no database, and no event loop. A build reads your files and writes
a directory of static assets; any host that serves files can serve it.

Two things produce output, and it is worth knowing which is which:

<CardGrid>
  <Card title="Every build" icon="rocket">
    `grove check`, `astro dev`, and `astro build` all run the same pipeline:

    - HTML pages for records, collections, taxonomy, and your own routes.
    - `data/generated/records.full.json`, `records.index.json`, `records.json`,
      `site-config.json`.
    - `public/sitemap.xml`, `public/llms.txt`, `public/llms-full.txt`.
    - `public/og/**` — social cards rendered with satori at build time.
    - `public/robots.txt` and `public/og-image.svg`, until you edit them; editing one
      takes ownership and Grove stops regenerating it.
  </Card>
  <Card title="On demand" icon="setting">
    These are separate commands, usually run on a schedule rather than in a build:

    - `grove sync github` — refreshes the `github.*` block inside your record files.
    - `grove sync contributors` — writes `data/generated/contributors.json` and
      `repo-stats.json`.
    - `grove cleanup` — writes `data/generated/cleanup-report.json`.
    - `grove readme generate` — rewrites the block between the README sentinels.
  </Card>
</CardGrid>

<Aside type="caution" title="A common misreading">
  `grove check` does **not** regenerate everything under `data/generated/`.
  `contributors.json`, `repo-stats.json`, and `cleanup-report.json` live there but are
  written only by the commands above.
</Aside>

## The commands

`grove init` scaffolds a space. `grove check` validates and rebuilds. `grove update`
takes upstream UI changes without overwriting your edits. `grove sync` refreshes
external facts. `grove cleanup`, `grove audit`, `grove readme generate`,
`grove collection`, `grove icons`, and `grove import` handle the rest.

Every command, every flag, and every file each one writes is in the
[CLI reference](/reference/cli/).
