<Aside type="tip" title="Should I trust this entry?">
Health signals answer one question for the visitor of your directory: **"Should I trust this entry?"** A record with `status: active` and `tier: curated` says "yes, this is current and well-maintained". A record with `status: archived` says "the maintainer archived the upstream repo". A record with `status: unknown` says "we have no GitHub data — proceed with caution".
</Aside>

This guide is for site maintainers triaging the periodic cleanup report. If you're a contributor adding a single record, see [Author a record](/content/author-a-record/).

## Where the health data comes from

The `health` block on a record — `status`, `maturity`, `tier`, `visibility`, `cleanupCandidate`, `staleReason`, `confidence`, and `reasons` — is computed by `classifyHealth` (`packages/core/src/health.ts`), Grove's single source of truth for deriving these fields from a record's GitHub metadata (`github.*`).

Treat `health.*` as computed, not hand-authored: don't edit `status`, `maturity`, `tier`, `visibility`, `cleanupCandidate`, or `confidence` directly. To change a record's effective visibility, write a [decision](/concepts/decisions/) in `data/decisions.yml` instead — it overrides `health.visibility` without touching the rest of the block.
(`data/health.yml` is a legacy format the validator no longer parses.)

`reasons` is a plain-language array explaining the classification — e.g. `"Recent repository activity"`, `"No recent commits in the last 6 months"`, `"Strong adoption with maintenance signals"`, `"Clear license found"`, `"License is missing or unclear"`. It's for humans reading the raw record, not rendered to visitors.

## The status enum

Ten enum values. Seven come out of `classifyHealth`'s branching logic on GitHub metadata; three (`historical`, `quiet`, `unavailable`) never do — they only appear in a record if someone wrote them in by hand.

  <Card title="active">
    <Badge text="derived" variant="success" size="small" />

    **When:** Repo pushed within the last 183 days.

    **Action:** Leave alone.
  </Card>
  <Card title="mature">
    <Badge text="derived" variant="success" size="small" />

    **When:** Would otherwise be `active`, plus ≥ 500 stars, plus a release in the last 365 days or a clear (non-`NOASSERTION`) license.

    **Action:** Nothing to do — this is the top tier already.
  </Card>
  <Card title="stale">
    <Badge text="derived" variant="success" size="small" />

    **When:** Last push more than 183 days ago, up to 548 days (roughly 6–18 months).

    **Action:** Decide: still relevant?
  </Card>
  <Card title="needs_review">
    <Badge text="derived" variant="success" size="small" />

    **When:** Last push more than 548 days ago, up to 730 days (roughly 18–24 months) — the gap between `stale` and `inactive`.

    **Action:** Read the repo; decide `keep`, `hide`, or `historical`.
  </Card>
  <Card title="inactive">
    <Badge text="derived" variant="success" size="small" />

    **When:** Last push more than 730 days ago (24+ months).

    **Action:** Add a `historical` or `remove` decision.
  </Card>
  <Card title="archived">
    <Badge text="derived" variant="success" size="small" />

    **When:** GitHub reports the repo as archived.

    **Action:** Add a `hide` or `historical` decision.
  </Card>
  <Card title="unknown">
    <Badge text="derived" variant="success" size="small" />

    **When:** No GitHub metadata at all (e.g., the project isn't on GitHub).

    **Action:** Add a `repoUrl`, or write a decision explaining why it's listed anyway.
  </Card>
  <Card title="historical">
    <Badge text="editor-only" variant="caution" size="small" />

    Hand-set on the record; kept for reference, not promotion. `classifyHealth` never produces this value.
  </Card>
  <Card title="quiet">
    <Badge text="editor-only" variant="caution" size="small" />

    Hand-set on the record; "watch this one". `classifyHealth` never produces this value.
  </Card>
  <Card title="unavailable">
    <Badge text="editor-only" variant="caution" size="small" />

    Hand-set on the record; the upstream repo couldn't be checked (404 / rate-limit / private). `classifyHealth` never produces this value.

    **Action:** Treat like `archived` for visibility.
  </Card>
</CardGrid>

`needs_review` is a real output of `classifyHealth`, not an editor-only value — it's what a repo classifies as when its last push falls between the `stale` and `inactive` windows. Only `historical`, `quiet`, and `unavailable` are hand-authored; `data/decisions.yml` has no field for `status`, so these three can only be set by editing the record's `health.status` directly.

## The maturity field

`maturity` is separate from `status` — a project can be `status: active` with `maturity: experimental`. Four values:

- **`unknown`** — `status` is `archived` or `inactive`.
- **`mature`** — the same bar as the `mature` status: ≥ 500 stars plus a recent release or clear license, on a repo pushed within 183 days.
- **`useful`** — ≥ 50 stars, or a repo pushed within 183 days that has a recent release or clear license, without meeting the `mature` bar.
- **`experimental`** — none of the above.

## The tier enum

Four values, derived from stars and `status`.

<CardGrid>
  <Card title="curated" icon="star">
    ≥ 500 stars. The record goes to the top of the index. The only signal that triggers `curated` is star count — there is no "active months" rule in the code.
  </Card>
  <Card title="listed">
    ≥ 50 stars. The default tier for established projects.
  </Card>
  <Card title="experimental">
    Fewer than 50 stars. Not a punishment — it means "we don't have enough data to vouch for this yet".
  </Card>
  <Card title="hidden">
    Status is `archived` or `inactive`. The record is still in the data, but the index does not list it. (Not `archived/unavailable` — `unavailable` is an editor-only status and does not drive `hidden` on its own.)
  </Card>
</CardGrid>

`curated` vs `listed` is purely a function of stars. Promotion isn't an editor decision; it's a function of the project's adoption. If you want to *override* the tier, use a decision.

## The cleanupCandidate flag

<Aside type="note" title="When cleanupCandidate is true">
`health.cleanupCandidate` is `true` only when `status` is `stale`, `archived`, or `inactive`. It's explicitly `false` when there's no GitHub data at all (`status: unknown`) — the flag itself doesn't cover that case.

`grove cleanup` casts a wider net than the flag: it writes `data/generated/cleanup-report.json` with every record where `health.cleanupCandidate` is `true`, **or** `health.status` is `unknown`, **or** `health.status` is `needs_review`. Run `grove cleanup` (locally or in CI) to regenerate the report — nothing regenerates it automatically on a schedule.
</Aside>

## A triage session

When the cleanup report lands, work through it in this order. Don't try to handle all 200 candidates in one PR — break it into batches of 10-20.

<Steps>

1. **Open `data/generated/cleanup-report.json`.** Sort by `staleReason` (`no_commits_365_days`, `no_commits_24_months`, or `github_archived`). Records sharing a `staleReason` are usually batchable with the same decision and justification.

2. **For each `archived` candidate**: visit the live repo to confirm the archive notice is there. If the project is *also* superseded by something in your directory, add a `historical` decision and note the replacement in `reason`. If it's just dead, add `remove`.

3. **For each `stale` or `needs_review` candidate**: read the last commit. If the project is feature-complete (a library that hit 1.0 and stopped), add a `keep` decision. If it was abandoned without being archived, this is a judgment call — `hide` is the safe default; `remove` if the GitHub repo is also gone.

4. **For each `unknown` candidate**: usually means the project isn't on GitHub. Either add the correct `repoUrl` so a future sync can classify it, or write a decision noting where it actually lives.

5. **Run `grove check` after each batch** to make sure `data/decisions.yml` parses and the generated index still validates.

</Steps>

## When signals lie

The signals are heuristics. Three common cases where they get it wrong:

<Aside type="caution" title="No commits in 18 months but the project is feature-complete">
A library at 1.0 with a stable API has every right to be quiet. Don't auto-`hide` these — write a `keep` decision instead.
</Aside>

<Aside type="caution" title="Fewer than 50 stars but it's a brand-new launch">
`experimental` is correct — the tier reflects "we don't have adoption data yet", not "this is bad". Don't write a decision to override the tier; let it climb as stars arrive.
</Aside>

<Aside type="caution" title="The GitHub repo was transferred">
The sync step will see the new owner and the new push dates. If the project is the same project under new stewardship, just let it sync. If the new owner is unrelated, treat it as `unavailable` and remove.
</Aside>

## Confidence

`confidence` is `low`, `medium`, or `high`, and the rule is narrower than it looks: it's `low` only when there's no GitHub metadata at all; otherwise it's `high` when the record's `github.fullName` is set, and `medium` when it isn't. License and recent-activity data don't factor into confidence — only whether GitHub returned a `fullName` for the repo.

<CardGrid>
  <Card title="low" icon="warning">
    No GitHub metadata at all.
  </Card>
  <Card title="medium">
    GitHub metadata exists, but `fullName` (the `owner/repo` identifier) isn't set.
  </Card>
  <Card title="high" icon="star">
    GitHub metadata exists and `fullName` is set.
  </Card>
</CardGrid>

Low confidence doesn't mean the record is bad — it means "we're guessing, not measuring". A `low`-confidence record that's been around for two years and still has community traction is fine; the heuristic just can't see it.

## What "fixing" a record looks like

If you want a record to surface better in the index:

- **Stars are below 50, but you think it deserves `listed`?** You can't promote by hand — `tier` is a function of star count and `status`. The only legitimate override is a decision setting `visibility: highlight` so the record is editorially featured regardless of tier; `tier` itself stays `experimental`, since visibility and tier are separate axes.
- **Stars are above 500 but the record is still `experimental`?** The record's `health` block hasn't been recomputed against the current star count yet.
- **The record is `hidden` but you want it back?** It's `hidden` because `status` is `archived` or `inactive`. Resolve the underlying status first (most often: the upstream repo came back to life), or add a decision to override `visibility` directly.

See [Sync GitHub metadata](/automation/sync-github/) for how `github.*` — the metadata `classifyHealth` reads — gets onto a record.

## How overrides work

<Aside type="tip" title="What actually controls effective visibility">
For a project record, the index reads effective visibility from `health.visibility` alone — a bare top-level `visibility:` key on the record is not consulted there. `health.visibility` is derived from `tier`: `hide` when `tier` is `hidden` (i.e. `status` is `archived` or `inactive`), `keep` otherwise.

A `data/decisions.yml` entry overrides `health.visibility` directly — this is the supported way to set a record to `highlight`, `needs_review`, `hide`, `remove`, or `historical` regardless of what `classifyHealth` derived.
</Aside>
