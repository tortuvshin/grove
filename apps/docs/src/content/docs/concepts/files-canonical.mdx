Every piece of truth in a Grove space lives in a file a human can edit. The build pipeline reads them; every generated artifact (HTML pages, JSON datasets, sitemap, OG images, `llms.txt`) is derived.

<Aside type="note" title="The single rule">
  If you want to know what is true on the site, look at the files.
</Aside>

The corollary is the discipline it asks for: editors don't log in, they edit. PRs are the change-of-record. Generated artifacts are disposable; running `grove check` regenerates them.

## What this buys you

<CardGrid stagger>
  <Card title="Diffability" icon="document">
    <Badge text="+" variant="success" size="small" />
    Every change to your site is a `git diff`. Reviewers can read it. Tools can lint it. Backups are `git clone`.
  </Card>
  <Card title="Portability" icon="open-book">
    <Badge text="+" variant="success" size="small" />
    The state of your space is a folder of files. Move it to a new host, change deployment providers, hand it to a new maintainer. No vendor lock-in.
  </Card>
  <Card title="Auditability" icon="list-format">
    <Badge text="+" variant="success" size="small" />
    A record changed because someone changed a file. There is no other way it changed.
  </Card>
  <Card title="Recoverability" icon="setting">
    <Badge text="+" variant="success" size="small" />
    If a build goes wrong, the build pipeline is reproducible from the source files. There is no operator pager for "the database is in a bad state."
  </Card>
</CardGrid>

## What this costs you

<CardGrid stagger>
  <Card title="Discipline" icon="pencil">
    <Badge text="-" variant="danger" size="small" />
    Editors need a git workflow. There is no browser-based WYSIWYG.
  </Card>
  <Card title="No realtime" icon="info">
    <Badge text="-" variant="danger" size="small" />
    Changes ship when the next build runs. There is no live preview that the visitor sees.
  </Card>
  <Card title="No cross-record transactions" icon="warning">
    <Badge text="-" variant="danger" size="small" />
    Saving a record means running `grove check` again, not a single atomic update.
  </Card>
</CardGrid>

If those costs are too high, a different tool is the right tool. Files-first is a deliberate constraint, not a default.

## The three-tier model

Every file in a Grove space falls into exactly one of three tiers. Knowing which tier a
file is in tells you whether you may edit it.

<CardGrid stagger>
  <Card title="Author-owned" icon="pencil">
    Files a human edits by hand, in an editor, in a pull request:

    - **Records** — `data/records/<slug>.yml`. One typed entity per file.
    - **Markdown bodies** — `content/records/<slug>.md`. Optional long-form content.
    - **Taxonomy** — `data/taxonomy/*.yml`. Six controlled vocabularies.
    - **Decisions** — `data/decisions.yml`. Curator overrides for visibility and sort priority.
    - **Collections** — `data/collections/<slug>.yml`. Curated or ranked groupings.
    - **Content pages** — `content/pages/<slug>.md`. Standalone pages that aren't a record.
    - **Configuration** — `grove.config.ts`. Identity, routes, facets, theme, integrations.

    PR review is the change-of-record. Editors don't log in.
  </Card>

  <Card title="Derived" icon="setting">
    Files Grove writes on every build. Disposable and reproducible:

    - HTML pages — `/`, `/projects/`, `/projects/<slug>/`, `/collections/<slug>/`, and the rest.
    - JSON datasets — `data/generated/records.full.json`, `records.index.json`,
      `records.json`, `site-config.json`.
    - `public/sitemap.xml`, `public/llms.txt`, `public/llms-full.txt`.
    - `public/og/**` — satori-rendered social cards, namespaced by page type
      (`og/home.png`, `og/records/<slug>.png`, `og/collections/<slug>.png`, and so on).

    Every derived artifact is a pure function of the source files plus `grove.config.ts`.
    Never hand-edit them; the next build overwrites the diff.

    Two files are the exception. `public/robots.txt` and `public/og-image.svg` are
    generated with an ownership marker: edit either one and Grove stops regenerating it,
    leaving your version alone.
  </Card>

  <Card title="Refreshed facts" icon="rocket">
    Fields that machines re-write but humans never edit:

    - `github.{stars,forks,language,topics,license,...}` — refreshed by `grove sync github`.
    - `health.{status,maturity,tier,visibility,cleanupCandidate,...}` — derived from
      GitHub signals plus the freshness rules in `packages/core/src/health.ts`.
    - `data/generated/contributors.json` and `data/generated/repo-stats.json` —
      aggregated by `grove sync contributors`.
    - The README block bounded by `<!-- grove-readme:start/end -->` — rewritten by
      `grove readme generate`. Text outside the sentinels survives untouched.

    These blocks live inside author-owned files but are owned by Grove. The merge
    contract guarantees curator edits outside the sync surface survive a re-run.
  </Card>
</CardGrid>

<Aside type="tip" title="The central rule">
**Machines refresh facts. Maintainers make editorial decisions.**

`grove sync github` writes `github.*`. `grove cleanup` writes a triage report. Neither
deletes a record, changes `visibility`, or alters curator prose.

Decisions about which records to keep, hide, demote, or surface live in the record YAML
itself or in `data/decisions.yml`.
</Aside>

## What you'll edit day-to-day

In a typical day, a curator touches:

<Steps>
1. `data/records/<slug>.yml` — adding, renaming, retagging records.
2. `data/taxonomy/*.yml` — adding category/stack entries.
3. `data/decisions.yml` — overriding visibility, sort priority.
4. `content/records/<slug>.md` — writing the long-form body.
5. `data/collections/<slug>.yml` — curating a new collection.
</Steps>

Everything else is regenerated.

## Try it

A minimal scaffolded space looks like this:

<FileTree>
- my-space/
  - data/
    - records/             # author-owned: one .yml per record
    - taxonomy/            # author-owned: categories, stacks, platforms, ...
    - collections/         # author-owned: curated groupings
    - decisions.yml        # author-owned: visibility overrides
    - generated/           # DERIVED — never hand-edit, regenerated by `grove check`
  - content/
    - records/             # author-owned: markdown bodies for records
    - pages/               # author-owned: standalone pages
  - public/
    - og/                  # DERIVED — satori-rendered OG cards
  - src/pages/             # consumer-owned routes
  - grove.config.ts        # author-owned: identity, blueprint, facets, theme
</FileTree>

Confirm your own setup in one command:

```bash
pnpm exec grove check
```

If validation passes, the build-time part of the derived tier is up to date with your
sources: the records and site-config JSON, the sitemap, the `llms` files, and the OG
cards. The three files written by other commands — `contributors.json`,
`repo-stats.json`, and `cleanup-report.json` — also live under `data/generated/` but are
not touched by `grove check`.
