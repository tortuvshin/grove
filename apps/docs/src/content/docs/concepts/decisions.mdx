<Aside type="tip" title="Curators are the source of authority">
  Curators shape how a Grove space presents its records through two surfaces. The decisions file is the single source of truth across the whole site for overrides — it carries reviewer identity, timestamps, and reasons that the record-level fields do not.
</Aside>

Curators shape how a Grove space presents its records through two surfaces:

1. **The record's own YAML** — `curation.{reviewed,reviewedBy,reviewedAt,notes,labels,lenses}` and `scores`.
2. **`data/decisions.yml`** — site-level overrides keyed by record id. Each entry changes how one record is presented.

The record-level fields are usually enough. `data/decisions.yml` is for the cases where a curator wants one source of truth across the whole site rather than editing many records.

## Visibility

`visibility` is the canonical signal for "should the visitor see this record?"

<CardGrid>
  <Card title="highlight">
    <Badge text="highlight" variant="default" />

    Listed, marked for editorial emphasis. No automatic sort boost — pair it with a collection or a lens if you want it surfaced first.
  </Card>

  <Card title="keep">
    <Badge text="keep" variant="default" />

    Default. Listed normally.
  </Card>

  <Card title="needs_review">
    <Badge text="needs_review" variant="caution" />

    A record marked for human attention. Not a lens or a UI-level filter — nothing excludes or highlights it automatically.
  </Card>

  <Card title="hide">
    <Badge text="hide" variant="caution" />

    Excluded from listings and search. Direct links still resolve.
  </Card>

  <Card title="remove">
    <Badge text="remove" variant="danger" />

    Excluded from listings and search, same as `hide`. Signals the record shouldn't come back. The record YAML remains in git.
  </Card>

  <Card title="historical">
    <Badge text="historical" variant="note" />

    A record kept for reference, not promotion. Like `needs_review`, this is a status you set — it isn't a filter or a lens on its own.
  </Card>
</CardGrid>

`hide` and `remove` behave identically for the record's own detail page — a direct link resolves normally either way; there is no tombstone. Both are excluded, the same way, from listings, search, the sitemap, and llms output. The difference between them is intent, not mechanics: `remove` signals the record shouldn't be listed anywhere going forward, `hide` is often temporary.

## What lives on the record vs in `data/decisions.yml`

`curation.labels`, `curation.lenses`, and `curation.notes` are editorial judgement that belongs on the record itself — edit `data/records/<slug>.yml` directly for these.

Visibility is different for project records (the only blueprint Grove ships today). The index reads a project's effective visibility from `health.visibility`, not from a top-level `visibility:` key on the record — so adding `visibility: highlight` to the top of a project record's YAML has no effect on what's listed. `health.*` is not refreshed by any command — see [Health classification](/content/health-classification/). Use `data/decisions.yml` instead: a decision's `visibility` is folded into the record's effective `health.visibility` when the site is built.

Use `data/decisions.yml` when:

- You want to change what a project record's listing visibility resolves to.
- The override should be visible at a glance, in one file, rather than scattered across records.
- The override needs `reason` plus `reviewedBy` / `reviewedAt` — metadata a record's own YAML has no field for.

<Tabs syncKey="where">
  <TabItem label="Record" icon="document">
    Curation labels, lenses, and notes are editorial judgement — edit them directly on the record.

    ```yaml
    # data/records/<slug>.yml
    curation:
      labels: [hot]
      lenses: [good-to-learn]
      notes: Strong docs; recommend for the learning lens.
    ```
  </TabItem>

  <TabItem label="Decisions file" icon="setting">
    Use `data/decisions.yml` to override a record's effective visibility, with `reason`, `reviewedBy`, and `reviewedAt` carried alongside it.

    ```yaml
    # data/decisions.yml
    - id: my-record
      decision:
        visibility: hide
        reason: Archived in 2024; awaiting re-launch announcement.
        reviewedBy: maintainer-name
        reviewedAt: "2026-04-01"
    - id: another-record
      decision:
        visibility: highlight
        reason: Reviewed and re-curated for the 2026 launch.
    ```
  </TabItem>
</Tabs>

## `data/decisions.yml` shape

```yaml
# data/decisions.yml
# data/decisions.yml accepts either a list or { decisions: [...] }
- id: <record-slug>
  decision:
    visibility: <enum>
    reason: <string, ≥1 char>
    reviewedBy: <string, optional>
    reviewedAt: <string, optional ISO timestamp>
```

Each entry must include `id` (matching a record `slug`) and `decision.visibility` plus `decision.reason`. The optional fields identify who reviewed and when.

## Curation labels

`curation.labels` is a curator-applied tagging system that's independent of `tags`. The accepted values are `new`, `hot`, `mature`, and `featured`:

<CardGrid>
  <Card title="hot">
    <Badge text="hot" variant="caution" />

    Has a dedicated lens: `?lens=hot` (equivalently `?label=hot`) filters to records carrying this label.
  </Card>

  <Card title="mature">
    <Badge text="mature" variant="success" />

    Has a dedicated lens: `?lens=mature` (equivalently `?label=mature`) filters to records carrying this label.
  </Card>

  <Card title="new">
    <Badge text="new" variant="tip" />

    No dedicated lens. Filterable directly via `?label=new`, and renders as a "Recently added" badge.
  </Card>

  <Card title="featured">
    <Badge text="featured" variant="default" />

    No dedicated lens. Filterable directly via `?label=featured`, and renders as a "Featured" badge.
  </Card>
</CardGrid>

A record can carry several labels. None of the four labels are computed automatically — a curator applies them by hand in `curation.labels`. See [Lens recipes](/discovery/lens-recipes/) for the full lens list.

## Scores

`scores.{activity,maturity,learning,contribution,docs,overall}` is a 0-100 scale per axis. The framework uses `overall` as the default ranking when no other sort is selected.

## What curators should never do

<Aside type="danger" title="Never edit generated files">
  Don't edit generated files under `data/generated/`. They are pure output.
</Aside>

<Aside type="danger" title="Never manually set health fields">
  To change a record's effective visibility, write a `data/decisions.yml` entry rather than editing `health.visibility` by hand — the decision is folded in at build time and leaves the rest of the health block alone.
</Aside>

<Aside type="danger" title="Never delete a record to remove it">
  Don't delete a record to "remove" it. Add a `data/decisions.yml` entry with `decision.visibility: remove` instead. The record YAML stays in git; only the effective visibility changes.
</Aside>

## Fields reference

`data/decisions.yml` accepts a list of entries, or `{ decisions: [...] }` wrapping the same list. Each entry:

| Field | Type | Required | Description |
|---|---|---|---|
| `id` | string | yes | Matches a record's `slug`. |
| `decision.visibility` | `highlight` \| `keep` \| `needs_review` \| `hide` \| `remove` \| `historical` | yes | Overrides the record's effective visibility. |
| `decision.reason` | string | yes | Curator note; not surfaced publicly by default. |
| `decision.reviewedBy` | string | no | Who made the call. |
| `decision.reviewedAt` | string | no | ISO timestamp. |

There is no `sortPriority`, `pin`, or `renameSlug` field — `decision.visibility` is the only lever a decision has over what's rendered.

When a decision and a record's own state disagree (e.g., the record has no `health` block but the decision says `hide`), the decision wins — it's folded into the record's effective `health.visibility` before the site is built.
