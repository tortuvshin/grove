Every output Grove produces is fully static. No runtime, no server, no database. Deployment is `pnpm build` + upload to a CDN.

<Aside type="tip" title="Static-first philosophy">
  Grove deliberately avoids runtime, databases, and servers. The build pipeline is the entire backend; everything else is static bytes served by a CDN.
</Aside>

## What gets deployed

Everything under `dist/` after `pnpm build`:

- **HTML pages** — every route's static output (`/`, `/projects/`, `/projects/<slug>/`, `/collections/<slug>/`, etc.).
- **JSON datasets** — `records.json` and others under `data/generated/`, copied into the build.
- **`sitemap.xml`**, **`robots.txt`**, **`llms.txt`**, **`llms-full.txt`** — emitted to `public/` then copied into the build.
- **`public/og/<page>.png`** — satori-rendered OG cards.
- **`public/icons/**`** — the packaged icon set, with per-file ownership preserved.
- **`manifest.json`** — referenced by the Starlight docs site via `<link rel="manifest">`. Consumers provide their own; the default scaffold does not.

A typical `dist/` after `pnpm build` looks like this (abridged):

<FileTree>
- dist/
  - index.html                  # homepage
  - projects/
    - index.html                # project directory index
    - \<slug\>/
      - index.html              # one per record
  - collections/
    - index.html                # collections index
    - \<slug\>/index.html       # one per collection
  - data/
    - records.json              # full record list (searchable)
    - records.full.json         # record + body content
    - site-config.json          # identity, nav, facets
  - sitemap.xml
  - robots.txt
  - llms.txt
  - llms-full.txt
  - og/\<page\>.png             # satori-rendered OG cards
  - _astro/                     # hashed CSS / JS
</FileTree>

The build is deterministic: the same source files plus the same `grove.config.ts` produce the same output. There is no clock-dependent content unless the curator puts time strings in their data.

## Where the build runs

The build pipeline runs on three events:

<Tabs syncKey="trigger">
  <TabItem label="Local dev" icon="rocket">
    `pnpm dev` (which runs `astro dev`). The Astro integration invokes `prepareDirectory()` from `@grove-dev/core` on every `astro:config:setup`, so a save in `data/records/*.yml` produces an updated dataset within a few hundred milliseconds.
  </TabItem>
  <TabItem label="CI on push" icon="setting">
    `.github/workflows/ci.yml` runs `grove check` and Astro build.
  </TabItem>
  <TabItem label="Scheduled maintenance" icon="info">
    `sync-github.yml`, `sync-contributors.yml`, `cleanup.yml`, `readme.yml` re-run periodically and commit. The next push triggers another CI run that rebuilds.
  </TabItem>
</Tabs>

There is no separate "refresh" step required. The framework regenerates everything from sources on every build.

## Static-host expectations

A Grove site deploys to any static host. The scaffold has first-class workflows for Cloudflare and GitHub Pages, and recipe-style notes for Vercel, Netlify, and self-hosted setups — see [Deployment](/deployment/overview/).

For any host:

<CardGrid>
  <Card title="dist/ is the upload root" icon="document">
    Upload the contents of `dist/` to your static host's web root. Everything the site needs is in there.
  </Card>
  <Card title="404 handling" icon="warning">
    404s use `404.html` (Astro emits this automatically).
  </Card>
  <Card title="Trailing slash" icon="right-arrow">
    `trailingSlash: 'ignore'` is the Astro default — both `/about/` and `/about` work.
  </Card>
  <Card title="Cache headers" icon="setting">
    Cache headers are the host's responsibility. Set `Cache-Control: public, max-age=300, s-maxage=600` for HTML and one year for assets the framework generates (sitemap, OG cards, JSON datasets).
  </Card>
</CardGrid>

## What the host needs to know

<Aside type="note" title="The site URL">
  The site URL is configured in `site.url` in `grove.config.ts`. The framework writes it into:
</Aside>

- Every `<link rel="canonical">` and JSON-LD `url`.
- Every `og:url` and Twitter `url` meta tag.
- `og-image.svg` host references.
- The OG card manifest (`og-manifest.json`).
- The `llms.txt` link block.

If you change `site.url`, rebuild — there's no other source of truth for the URL.

## Why static-first is durable

<CardGrid stagger>
  <Card title="No runtime patching" icon="setting">
    <Badge text="+" variant="success" size="small" />
    A new feature ships as a new file in `dist/`. There's no daemon to redeploy.
  </Card>
  <Card title="No database migrations" icon="document">
    <Badge text="+" variant="success" size="small" />
    Schema changes are evident in `git log`; old builds keep working until you deploy the new one.
  </Card>
  <Card title="No surprise breakage at scale" icon="rocket">
    <Badge text="+" variant="success" size="small" />
    Static sites can be cached aggressively at the CDN edge; the framework is fine with that.
  </Card>
  <Card title="Cheap to host" icon="star">
    <Badge text="+" variant="success" size="small" />
    Static bytes are cheaper than compute by orders of magnitude.
  </Card>
</CardGrid>

The tradeoff is the same as every static site: changes go through a build. Curators accepting this constraint are the users Grove is built for.
