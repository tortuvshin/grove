<Aside type="note" title="What a content page is">
A Grove content page is a Markdown file at `content/pages/<name>.md` (the directory is `paths.pagesDir` in `grove.config.ts`, default `content/pages`). It's for prose that isn't a record, a collection, or a curated list — an about page, a contributing guide, a methodology write-up, a glossary entry.
</Aside>

## How it differs from a record

A record (`data/records/<slug>.yml`) is structured data: a `kind`, a `category`, taxonomy references, optionally a `content/records/<slug>.md` body attached to it. It gets a generated detail page, appears in browse filters, and can be synced from GitHub.

A content page is just Markdown. It has no `kind`, no taxonomy, no generated route of its own — a `.astro` file under `src/pages/` decides where it renders and supplies its own title, description, and SEO.

## How it renders

Grove doesn't auto-route content pages. Each one is wired up by a small, consumer-owned Astro page that reads the Markdown and decides what to do with it. The one pre-wired example in the CLI scaffold is the About page:

```astro title="src/pages/about.astro"
---
import BaseLayout from "@grove-dev/astro/layouts/BaseLayout.astro";
import siteConfig from "@grove/generated/site-config.json";
import { getPageContentHtml } from "@grove-dev/astro/server";

const pageContentHtml = getPageContentHtml("about");
---

<BaseLayout title="About" description="About this site" site={siteConfig}>
  {pageContentHtml ? (
    <section class="grove-prose" set:html={pageContentHtml} />
  ) : (
    <p>Default fallback copy, hard-coded in this page.</p>
  )}
</BaseLayout>
```

`getPageContentHtml(name)` (exported from `@grove-dev/astro/server`) looks for `content/pages/<name>.md`, strips any leading frontmatter block, renders the remaining Markdown, and sanitizes it. It returns the HTML string, or `null` if the file doesn't exist — which is why `about.astro` falls back to hard-coded copy when no `content/pages/about.md` is present. `grove init` doesn't scaffold that file; adding one is opt-in.

<Aside type="caution" title="Frontmatter isn't read automatically">
  You can put a `---` frontmatter block at the top of the Markdown file for your own reference, but `getPageContentHtml` strips it and never parses it. Nothing derives the page's `<title>`, meta description, or OG image from it — the wrapping `.astro` page supplies those explicitly, the same as any other Astro page. Any `title:`/`description:` you write in the frontmatter is just a note to yourself.
</Aside>

Want more than one content page? Copy the pattern: write `content/pages/<name>.md`, then a matching `src/pages/<name>.astro` that calls `getPageContentHtml("<name>")`. See [Custom pages](/customize/pages/) for the full walkthrough, including the Astro-page and generated-record alternatives.

## Markdown allowlist

Content pages are sanitized with a narrower allowlist than record bodies — the pipeline is shared (Markdown → sanitize-html), but a page author's Markdown gets a more conservative prose-only tag set:

<CardGrid stagger>
  <Card title="Allowed" icon="star">
    Headings `h1`–`h4`, paragraphs, `br`/`hr`, lists, `strong`/`em`/`b`/`i`/`u`/`s`/`del`, links, `code`/`pre`, blockquotes, images.
  </Card>
  <Card title="Not allowed here" icon="warning">
    Tables, `div`, task-list checkboxes, `details`/`summary`, and inline styles are all stripped — they're part of the wider allowlist used for a record's `content/records/<slug>.md` body, not the content-page allowlist. Images aren't restricted to a host allowlist; only the URL scheme is checked (`http`, `https`, or `data`).
  </Card>
</CardGrid>

## When to write a content page

<CardGrid stagger>
  <Card title="About pages" icon="document">
    About / manifestos / contributing guides — the kind of pages that explain *who runs this site* and *why it's organized this way*.
  </Card>
  <Card title="Editorial introductions" icon="seti:notebook">
    Editorial introductions to a directory section — the human-readable frame around a collection of records.
  </Card>
  <Card title="Glossary entries" icon="open-book">
    Glossary entries that don't fit any record — terms and concepts worth defining without attaching them to a specific entry.
  </Card>
  <Card title="Editorial indexes" icon="list-format">
    Indexes that group multiple collections by editorial intent — pages that pull together collections into a curated narrative.
  </Card>
</CardGrid>

<Aside type="caution" title="What a content page is NOT">
- A disguised record. If it has a slug, an avatar, a category, a tag, and a description, it should be a record.
- A static landing page — those live in the consumer's `src/pages/index.astro` and can use any Astro component.
</Aside>

## Routing

<FileTree>
- src/pages/
  - about.astro         renders `content/pages/about.md` at `/about/` (pre-wired by the CLI scaffold)
- content/pages/
  - about.md
</FileTree>

The Astro integration doesn't own content pages' routes — they're consumer-owned. Beyond the pre-wired `about.astro`, adding a page means writing both the Markdown file and its `.astro` wrapper yourself.
