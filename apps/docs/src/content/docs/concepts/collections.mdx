<Aside type="tip" title="What a collection is">
  A collection is a curator-managed grouping at `data/collections/<slug>.yml`. Collections are how a Grove site surfaces **reasoned views** over the record set: "Top Flutter finance apps", "Reading list for new contributors", "Stable, well-tested tools only."
</Aside>

A collection is different from a lens in two ways:

- Lenses are pure functions of the record set — they ask "what does the data say?" A collection is what the curator says the data means.
- A collection has its own URL and SEO surface. Lenses do not.

## Two kinds

`CollectionKind` is `"curated" | "generated"` (`packages/core/src/collections.ts`). Both kinds have the exact same shape — a `query` and a `ranking` — and are resolved the same way at build time: `runCollection` filters the record set with `query` and orders the result with `ranking` (`packages/core/src/collector.ts:12-17`). Records can also be hand-picked with `entries` (see [Hand-picked entries](#hand-picked-entries)); `kind` only changes the eyebrow label the collection page renders (`packages/astro/src/pages/collections/[slug].astro:52`: `"Curated collection"` vs `"Generated collection"`).

<Tabs syncKey="kind">
  <TabItem label="curated" icon="seti:notebook">
    ```yaml
    # data/collections/<slug>.yml
    kind: curated
    ```

    `kind: curated` is what `grove collection promote --from /browse?... --slug <s>` produces (`packages/cli/src/collection-cli.ts:24`). Use it for a hand-curated slice a maintainer built by narrowing a browse view.
  </TabItem>

  <TabItem label="generated" icon="list-format">
    ```yaml
    # data/collections/<slug>.yml
    kind: generated
    ```

    `kind: generated` is for a collection assembled more mechanically — a broad query with no manual browse-and-promote step behind it. It runs through the identical `query`/`ranking` pipeline; only the page's eyebrow text differs.
  </TabItem>
</Tabs>

## Shape

```yaml
# data/collections/<slug>.yml
slug: top-flutter
kind: curated
title: Top Flutter apps
description: Hand-picked Flutter projects that demonstrate strong, well-maintained engineering.
query:
  stacks: [flutter]
  categories: [productivity, finance]
  excludeStatuses: [archived]
ranking:
  preset: quality         # quality | active | curated | recency | stars
seo:
  title: Top Flutter apps
  description: Hand-picked Flutter projects.
  index: true
editorial:
  introduction: A short intro shown above the list.
  selectionNote: Re-curated for the 2026 launch.
  lastReviewedAt: "2026-04-01"
```

## Hand-picked entries

A query can only say "every Flutter app over 500 stars". A page that answers *"which of these should I pick?"* needs a curator to choose the records and say something about each one:

```yaml
# data/collections/visual-llm-app-builders.yml
slug: visual-llm-app-builders
title: Visual LLM App Builders
description: Open-source tools for building LLM workflows on a canvas instead of in code.
content: ./content/collections/visual-llm-app-builders.md
entries:
  - slug: dify
    pinned: true
    note: The most complete of the three. Pick it when you need a workflow editor, retrieval and a hosted API in one deployment.
  - slug: flowise
    note: Lighter and quicker to stand up. Pick it when a single Node.js service is all you want to operate.
ranking:
  preset: curated
faq:
  - q: Can these run without a hosted account?
    a: Yes. Both ship a Docker Compose setup.
```

How `runCollection` resolves it (`packages/core/src/collector.ts`):

- **Membership is picks ∪ query matches.** An empty `query` matches every record, so it only takes part when it states at least one criterion — or when there are no `entries` at all. The example above lists exactly two records. Add `query: { stacks: [python] }` and every Python record joins after the picks.
- **A pick skips the query**, `excludeStatuses` included — it is the curator's call. It cannot bring back a record hidden or removed by `visibility`; those never reach a collection.
- **Order:** `pinned` picks first, in file order; everything else by `ranking`. Under `preset: curated` that means picks in file order, then query matches.
- **`note` replaces the record's description** for that entry, on the page and in the `ItemList` JSON-LD. When any entry has a note the page renders a numbered verdict list instead of the card grid, because a card clamps its description to two lines.

`grove check` reports a pick that is not a record (`collection_unknown_entry`, error), a pick that is hidden (`collection_hidden_entry`, warning) and a `content` path that does not exist (`collection_body_missing`, error).

A collection with no entries renders `noindex` and stays out of the sitemap — an empty list has nothing to rank for.

<Aside type="note" title="About FAQ rich results">
  Google shows the expandable FAQ treatment only for a small set of authoritative government and health sites. Add `faq` because the questions help the reader and because the markup tells crawlers and LLM pipelines which text is a question and which its answer — not for a SERP feature.
</Aside>

## `grove collection promote`

The fastest way to create a collection is to land on a browse URL — `/browse?stack=flutter&category=finance` — and promote it:

<Steps>
1. Run the promote command from the repo root. The `--from` URL is parsed with `URLSearchParams` (handles `&`, `=`, `+`, percent-encoded correctly).

   <Tabs syncKey="pkg">
     <TabItem label="pnpm" icon="rocket">
       ```bash
       pnpm exec grove collection promote \
         --from '/browse?stack=flutter&category=finance' \
         --slug top-finance-flutter \
         --title 'Top Flutter finance apps'
       ```
     </TabItem>

     <TabItem label="npm" icon="rocket">
       ```bash
       npx grove collection promote \
         --from '/browse?stack=flutter&category=finance' \
         --slug top-finance-flutter \
         --title 'Top Flutter finance apps'
       ```
     </TabItem>
   </Tabs>

2. Grove writes `data/collections/<slug>.yml` with `kind: curated`, `query` derived from the params, `ranking.preset: 'quality'`, `excludeStatuses: ['archived']`.

3. The directory tree is created if it doesn't exist.

4. **Does not** pre-fill a description; the curator adds one.
</Steps>

`--from` is required, `--slug` is required, `--title` and `--description` are optional.

## How collections appear in the build

- `/collections/<slug>/` — the collection's detail page (header, hero, ranked list).
- `/collections/` — index of all collections.
- The collection contributes to `data/generated/site-config.json` so the build pipeline knows which collections to pre-render.

The page template is in `@grove-dev/astro`'s `CollectionPage` component. Consumers customize via their own `src/pages/collections/*` if they need a different layout.

## Validation and ranking inputs

`grove check` parses every collection file with the same schema the build uses. A typo that used to produce a silently unfiltered page — `ranking: { preset: popularity }`, `minStars: "500"` — is a `collection_invalid` error; a slug shared by two files is `duplicate_collection_slug`; a query that matches nothing is a `collection_empty` warning. See [`grove check`](/automation/check/).

`excludeStatuses` matches a record's **`health.status`** (`active`, `mature`, `stale`, `inactive`, `archived`, …), the lifecycle value `grove sync github` writes — not the curation `visibility`, which is `keep` for almost every record. The `quality` and `active` presets rank on a curated `scores` block when you wrote one and otherwise on the synced GitHub data: recent releases, pushes and commits for activity, stars on a log scale for adoption. A directory that has run `grove sync github` gets meaningful ordering with no hand-scored records.

<Aside type="caution" title="Upgrading from 0.10">
  Before this change `excludeStatuses` compared against `visibility`, so `excludeStatuses: [archived]` excluded nothing, and records without a `scores` block all ranked 0 and rendered in file order. After upgrading, a collection can get shorter (archived or stale records now leave) and its order will change. If you wrote a local adapter to back-fill `status`, `pushedAt` or scores before calling `runCollection`, delete it.
</Aside>

## When to use a collection vs a content page

A content page is for prose. A collection is for "I want a page that lists and sorts records for me." If your collection page is mostly prose with one or two record mentions, write a content page. If it lists twenty records, that's a collection.

## How matching works

<Aside type="note" title="Match semantics">
  `filterEntries` ANDs every query field you set: a record must satisfy `stacks`, `platforms`, `categories`, `licenses`, `kinds`, `excludeStatuses`, `minStars`, `minForks`, and `q` all at once. Within a single array field (`platforms`, `categories`, `licenses`) a record matches if it has *any* of the listed values (`packages/core/src/collections.ts`).
</Aside>

If a record was added after the collection was created and now matches the query, it appears automatically at the next build — no re-authoring needed.
