title: "Walkthrough: sync GitHub metadata"
description: Refresh every record's github.* block with live stars, forks, language, topics, and license, end-to-end.
---

import { Aside, Card, CardGrid, FileTree, LinkButton, LinkCard, Steps, TabItem, Tabs } from '@astrojs/starlight/components';

<Aside type="note" title="Before you start">
  By the end of this walkthrough every record that has a `repoUrl` will have a populated `github.*` block. The walkthrough assumes you have at least one record with `repoUrl` set — if not, complete [Walkthrough: add your first record](/getting-started/first-record/) first.

  A token is not strictly required. Without one the sync calls the GitHub API unauthenticated, which is heavily rate-limited, and falls back to scraping the repo page when the API call fails. With more than a handful of records you want a token.
</Aside>

<Steps>

1. ## Create a GitHub token

   Go to **GitHub → Settings → Developer settings → Personal access tokens**. Pick the token type that matches your account:

   <Tabs syncKey="token">
     <TabItem label="Fine-grained" icon="setting">
       Create a token under **Fine-grained tokens** with:

       - **Resource owner:** your own user (or the org that owns the repos)
       - **Repository access:** "Public Repositories (read-only)"
       - **Permissions:**
         - `Metadata: Read-only`
         - `Contents: Read-only`
     </TabItem>
     <TabItem label="Classic" icon="document">
       Create a token under **Tokens (classic)** with the minimum scope:

       - **`public_repo`** — read public repositories (stars, forks, languages, topics, license).

       This is the only scope required for the sync. Do not grant extra scopes unless you have a specific reason.
     </TabItem>
   </Tabs>

2. ## Add the token to `.env`

   ```bash
   export GITHUB_TOKEN=ghp_…
   ```

   <Aside type="caution" title="The variable name matters">
     `grove sync github` reads `process.env.GITHUB_TOKEN` and nothing else — `GH_TOKEN` is **not** read by this command (`packages/core/src/github.ts`). `grove sync contributors` is the one that accepts either name.

     Grove's CLI does not load `.env` files. Export the variable in your shell, or use a runner that injects it, before calling the command. If you do keep it in a file, make sure that file is gitignored.
   </Aside>

3. ## Enable the GitHub integration

   Open `grove.config.ts` and enable the GitHub integration:

   ```ts title="grove.config.ts"
   integrations: {
     github: {
       metadata: true,     // refresh stars, forks, language, topics, license
       contributors: true, // aggregate contributor counts
     },
   }
   ```

   The dev server picks up the config change after a restart. Kill `pnpm dev` and re-run it.

4. ## Run the sync

   <Tabs syncKey="pkg">
     <TabItem label="pnpm" icon="seti:notebook">
       ```bash
       pnpm exec grove sync github
       ```
     </TabItem>
     <TabItem label="npm" icon="seti:notebook">
       ```bash
       npx grove sync github
       ```
     </TabItem>
     <TabItem label="bun" icon="seti:notebook">
       ```bash
       bunx grove sync github
       ```
     </TabItem>
   </Tabs>

   The command walks every record, calls the GitHub REST API for the repo at `repoUrl`, and writes back into the record YAML:

   - `github.repository` — `full_name`, `stargazers_count`, `forks_count`, `open_issues_count`, `language`, `pushed_at`, `updated_at`, `archived`, `disabled`, `default_branch`, `license`, and `topics`. Merged over whatever was already there, so extra keys you added survive.
   - `github.latestReleaseAt` and `github.homepage` — written only when GitHub returned them.
   - `github.sync` — `{ syncedAt, source }` provenance, where `source` is `api` or `html`.

   Everything it writes lands under `github.`. It does not touch `health`, `curation`, or any prose you wrote — the patch is merged into the existing `github` block, so fields outside the sync surface survive a re-run.

   <Aside type="note" title="What you should see">
     One line per record: `[sync github] <file>: api`, or `html` when the fallback handled it, or `no repository, skipped` / `invalid GitHub URL, skipped` / `unavailable`. The run ends with a count of updated, HTML-fallback, and failed records.
   </Aside>

   Two flags are worth knowing: `--limit <count>` processes only the first N record files (useful for a dry run), and `--strict` sets a non-zero exit code when any record failed.

5. ## Inspect the new fields

   Open any record that has a `repoUrl`:

   ```yaml title="data/records/astro.yml"
   kind: project
   name: astro
   repoUrl: https://github.com/withastro/astro
   github:
     repository:
       full_name: withastro/astro
       stargazers_count: 51234
       forks_count: 2678
       open_issues_count: 143
       language: TypeScript
       pushed_at: "2026-03-28T09:11:52Z"
       updated_at: "2026-03-28T09:11:52Z"
       archived: false
       disabled: false
       default_branch: main
       license:
         spdx_id: MIT
         name: MIT
       topics: [astro, static-site-generator, ssg]
     latestReleaseAt: "2026-03-20T16:04:00Z"
     homepage: https://astro.build
     sync:
       syncedAt: "2026-04-01T10:23:00Z"
       source: api
   ```

   <Aside type="caution" title="The sync does not derive a health block">
     Star counts do not promote a record's `tier`, and nothing here writes `health.*`. Health entries live in `data/health.yml` and are authored separately — see [Maintain health signals](/content/health-classification/).
   </Aside>

   <FileTree>
   - data
     - records
       - **astro.yml** _(gained a `github.*` block after sync)_
       - other-record.yml
   - grove.config.ts
   - package.json
   </FileTree>

6. ## Commit and open the PR

   ```bash
   git add data/records/*.yml
   git commit -m "Sync GitHub metadata"
   git push
   ```

   <Aside type="note" title="What you should see">
     the diff is contained to `github.*` blocks. Review it to confirm no curator content was overwritten — the merge keeps additions outside the sync surface, but a quick look costs nothing.
   </Aside>

</Steps>

<Aside type="tip" title="Schedule the sync">
  Don't run `grove sync github` by hand every week. `grove init` ships a `.github/workflows/sync-github.yml` that runs on a schedule and opens a pull request with the result rather than pushing to `main`:

  ```yaml
  # .github/workflows/sync-github.yml (already in the scaffold)
  on:
    schedule:
      - cron: "0 3 * * 0"   # every Sunday at 03:00 UTC
    workflow_dispatch:
  ```

  `secrets.GITHUB_TOKEN` is provided by Actions automatically — there is no secret to create.
</Aside>

<Aside type="caution" title="Check the env var name in the scaffolded workflow">
  The shipped workflow passes the token as `GH_TOKEN`. `grove sync github` reads `GITHUB_TOKEN`, so as written the step runs unauthenticated and leans on the rate-limited path. Until that is fixed upstream, change the step to:

  ```yaml
  - run: pnpm exec grove sync github
    env:
      GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
  ```
</Aside>
