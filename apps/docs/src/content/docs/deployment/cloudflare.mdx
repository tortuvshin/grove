<Aside type="tip" title="Cloudflare as a deploy target">
  Cloudflare serves static assets at the edge with very low latency. Grove ships no adapter and no `wrangler.toml` for either pattern below — you write the config file yourself, once.
</Aside>

Two deployment targets on Cloudflare work with a Grove space's `dist/` output:

1. **Cloudflare Pages** — the conventional static-site target.
2. **Workers-with-Assets** — the pattern this documentation site itself (`apps/docs/`, a separate Starlight project in the Grove monorepo, not a Grove space) uses, because Cloudflare's automatic Astro config injection pulls in `@astrojs/cloudflare`, whose Vite plugin has an unresolved `prismjs` dependency.

<Aside type="note" title="Prerequisites">
  - A Cloudflare account (the free tier works).
  - A Grove space that builds to `dist/` via `pnpm build`.
  - Neither pattern needs the `@astrojs/cloudflare` adapter — Grove's build is fully static (`astro build` with no `output` or `adapter` configured, which defaults to static output).
</Aside>

## Cloudflare Pages

Standard `wrangler pages deploy dist` flow.

<Steps>

1. Add a `wrangler.toml` at the project root:

   ```toml title="wrangler.toml"
   name = "your-site"
   pages_build_output_dir = "./dist"
   compatibility_date = "2024-09-01"
   ```

   Wrangler reads `pages_build_output_dir` and uploads the contents of `dist/` to the Pages edge. Set the build command (`pnpm build`) and output directory (`dist`) in the Cloudflare Pages dashboard's project settings, not in `wrangler.toml` — the Pages build environment reads those from the dashboard.

2. Deploy with the Pages CLI:

   <Tabs syncKey="pkg">
     <TabItem label="pnpm" icon="pnpm">
       ```bash
       pnpm build
       pnpm dlx wrangler pages deploy dist
       ```
     </TabItem>
     <TabItem label="npm" icon="npm">
       ```bash
       npm run build
       npx wrangler pages deploy dist
       ```
     </TabItem>
     <TabItem label="bun" icon="bun">
       ```bash
       bun run build
       bunx wrangler pages deploy dist
       ```
     </TabItem>
   </Tabs>

   A Pages project URL is printed by the CLI; the deploy becomes live at the edge shortly after.

3. Set the site URL: add `SITE_URL` as an environment variable in the Pages project's dashboard settings (Settings → Environment variables), pointing at your Pages URL or custom domain. `astro.config.mjs` reads `process.env.SITE_URL || groveConfig.site.url` — without a matching value, the build either fails (if `site.url` in `grove.config.ts` is also unset — the shared `Seo` layout throws when `Astro.site` is undefined) or ships with the wrong canonical URLs baked into `sitemap.xml`, OG tags, and `llms.txt`.

</Steps>

## Workers-with-Assets

This is the pattern the Grove documentation site (`apps/docs/`) actually uses in this monorepo, for the `prismjs` reason above. Its real `wrangler.toml`, unedited:

```toml title="apps/docs/wrangler.toml (real file, for reference)"
name = "grove"
compatibility_date = "2026-06-11"

[assets]
directory = "./dist"
```

Notice what's **not** here: no `main` entry point and no `[build]` block. There is no custom Worker script — a plain `astro build` with no adapter never emits a `dist/_worker.js/`, only the static `dist/` tree, so `[assets]` with just a `directory` is the entire config. The build command and output directory (`pnpm build`, `dist`) are set in the Cloudflare dashboard's project settings, exactly as with Pages — not inside `wrangler.toml`.

<Aside type="caution" title="Why this file exists at all">
  Without an `[assets]`/`[build]`-free `wrangler.toml`, Cloudflare's `runAutoConfig` detects an Astro project, downloads `@astrojs/cloudflare`, and injects it into `astro.config.mjs`. That adapter's Vite plugin imports `prismjs`, which is a `devDependency` of `@astrojs/cloudflare` and isn't bundled with it — the build then fails with `Cannot find package 'prismjs'`. Shipping your own minimal `wrangler.toml` skips the auto-config step entirely.
</Aside>

<Steps>

1. Write `wrangler.toml` as shown above, adjusting `name` and `compatibility_date` (use today's date or a recent one — Cloudflare accepts any past date).

2. Build and deploy:

   <Tabs syncKey="pkg">
     <TabItem label="pnpm" icon="pnpm">
       ```bash
       pnpm build
       pnpm dlx wrangler deploy
       ```
     </TabItem>
     <TabItem label="npm" icon="npm">
       ```bash
       npm run build
       npx wrangler deploy
       ```
     </TabItem>
     <TabItem label="bun" icon="bun">
       ```bash
       bun run build
       bunx wrangler deploy
       ```
     </TabItem>
   </Tabs>

   `wrangler deploy` (the Workers CLI, not `wrangler pages deploy`) uploads `dist/` as the Worker's static assets.

3. In the Cloudflare dashboard, set the project's Root directory, Build command, and Build output to match your repo layout (for a monorepo, Root directory is the path to your Grove space, e.g. `apps/example`), and add `SITE_URL` under the project's environment variables.

</Steps>

## Caveats

<Aside type="caution" title="prismjs resolution">
  This only bites you if something in your build pipeline pulls in `@astrojs/cloudflare` — Grove itself never adds it. If you don't add the adapter yourself and you ship the minimal `wrangler.toml` above, you won't hit this.
</Aside>

<Aside type="caution" title="Custom domain">
  Cloudflare Pages projects get domain/CNAME setup through the dashboard's Custom domains tab; Workers need a Route or Custom Domain binding configured separately (dashboard → Worker → Settings → Domains & Routes).
</Aside>

<Aside type="caution" title="Headers">
  Set custom headers (cache-control, security) in `public/_headers` — Cloudflare Pages and Workers-with-Assets both honor this file if it's present in the uploaded directory. Grove doesn't generate one; add it to `public/` yourself if you need it.
</Aside>
