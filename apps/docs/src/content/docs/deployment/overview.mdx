<Aside type="tip">
  The Astro build produces a fully static site. The build output is in `dist/` after `pnpm build`. There is no server runtime, no adapter, and no database — every host that serves static files works.
</Aside>

## Build command

<Steps>

1. Run the build:

    ```bash
    pnpm build
    ```

    This runs `astro build` — that's the entire `build` script in `package.json`. The Grove Astro integration (`@grove-dev/astro`) hooks into Astro's `astro:config:setup` and calls `prepareDirectory()` automatically before any page renders, so a plain `pnpm build` already:

    - regenerates `data/generated/*.json` from your records, taxonomy, and overrides,
    - writes `public/sitemap.xml`, `public/llms.txt`, `public/llms-full.txt`,
    - writes `public/robots.txt` and `public/og-image.svg`,
    - renders the per-page OG cards under `public/og/**`.

    No consumer-owned prebuild script is required — Astro's own build then turns all of this plus your pages into `dist/`.

    `grove check` (schema/data validation, then the same generation step, then `astro check`) is a stricter pre-flight gate used in `.github/workflows/ci.yml` on every push and pull request. It is **not** part of `pnpm build` and it is **not** run by the deploy workflow below — deploy only runs `pnpm build`.

2. Set the site URL for the production host:

    The canonical URL used for `sitemap.xml`, canonical/OG/Twitter tags, JSON-LD, and `llms.txt` comes from `site.url` in `grove.config.ts`, or from the `SITE_URL` environment variable, which `astro.config.mjs` prefers when it's set:

    ```js
    site: process.env.SITE_URL || groveConfig.site.url,
    ```

    If **neither** is set, `Astro.site` is `undefined` and the build fails outright — the shared `Seo` layout throws `Seo: \`site\` is not set on the Astro config` rather than silently emitting URLs on a domain you don't own. If `site.url` is set but wrong (still the scaffold's placeholder, or a typo), the build succeeds but every canonical link, sitemap entry, OG image, and the `llms.txt` `Site:` line silently point at the wrong domain.

    Set `SITE_URL` in the host's build environment (see each provider page for exactly where) so the same repo can build a preview under one domain and production under another without editing `grove.config.ts`.

</Steps>

Grove's reference app (`apps/example/` in the repo — `grove init` itself writes no workflows, so copy from there) ships only one deploy workflow: `.github/workflows/deploy.yml`, targeting GitHub Pages. Cloudflare, Netlify, and self-hosted are all "bring your own host config" — Grove ships no `wrangler.toml`, `netlify.toml`, or `Dockerfile`. Every host, including GitHub Pages, is just serving the same `dist/` folder — the differences are in CI setup, headers, and edge features, not in what Astro produces.

## Pre-deploy checklist

Before you point your domain at a new deploy:

<Steps>

1. `pnpm build` succeeds locally.
2. `dist/index.html` exists and contains your site name.
3. `dist/sitemap.xml` is present and lists your production domain, not `example.com`.
4. `dist/llms.txt` and `dist/llms-full.txt` are present.
5. A record's detail page exists on disk, e.g. `dist/<your-directory-route>/<some-slug>/index.html`.
6. `SITE_URL` (or `site.url` in `grove.config.ts`) is your real production domain, not the scaffold placeholder.
7. `pnpm preview` shows the site the way you expect.

</Steps>

## Continuous deployment

The reference app ships six GitHub Actions workflows under `.github/workflows/` (copy the ones you want — `grove init` doesn't write them); only `deploy.yml` deploys:

<CardGrid>
  <Card title="deploy.yml" icon="rocket">
    Push to `main` or manual dispatch. Builds with `pnpm build` and publishes `dist/` to GitHub Pages.
  </Card>
  <Card title="ci.yml" icon="document">
    Push to `main` and every pull request. Runs `pnpm exec grove check`, then `pnpm build` — no deploy step.
  </Card>
  <Card title="sync-github.yml" icon="document">
    Weekly cron. Refreshes stars/language/last-pushed from GitHub and opens a PR.
  </Card>
  <Card title="sync-contributors.yml" icon="document">
    Weekly cron. Aggregates contributor data and commits it directly.
  </Card>
  <Card title="cleanup.yml" icon="document">
    First Monday of the month. Posts a triage report to the job summary.
  </Card>
  <Card title="readme.yml" icon="document">
    Weekly cron. Regenerates the README's awesome-list block and opens a PR if it changed.
  </Card>
</CardGrid>

None of the scheduled workflows touch `dist/` or deploy anything — they update source files (`data/generated/*.json`, `README.md`) and either commit directly or open a PR. A merge to `main` is what triggers `deploy.yml`. See [Scheduled maintenance](/automation/scheduled/) for cadence and triggers.

## Local preview

Before pushing to a host, preview the production build locally:

```bash
pnpm build
pnpm preview
```

The `preview` script serves `dist/` on a local port. Walk through every page, check every filter, click every link before you push.
